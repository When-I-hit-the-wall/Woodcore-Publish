# The RFEM points of docs/open-questions.md (§14), as they stood when the RFEM import was retired (0.117)

- **What the RFEM work does not do yet** (v0.100, §3.3quindecies). None is blocked on a decision.
  - **The envelope's band.** A design situation's diagram is a max curve and a min curve at every station, and `envelopes.py` aggregates the stations away to the member's extreme. Keeping them behind a flag is where it starts; drawing two curves and the area between them is `diagram_svg`'s.
  - **The static models tab does not list an imported model at all.** `list_models` reads `Woodcore-Datei/statics/` and an imported model is not there, so the view file that carries the engineer's presentation can only be written by hand. Until the tab lists them — read-only for the geometry, with the quantity, the loading and the three sizes editable — the feature has no button. The engineer asked for it and for **«un bouton pour ajouter ce modèle à l'onglet Modèles statiques»** in the RFEM tab.
  - **The internal forces do not show in the RFEM tab**, which the engineer reported after the curves were repaired. Not diagnosed yet.
  - **The example project names no RFEM export**, so the six commands' examples are `typ-dry`, their copied calls are exempt from compiling, and **the website shows none of their tables**. Three widenings in `tests/test_commands.py` carry that reason and come back out the moment `tests/projet-exemple/` carries a small export.
  - **The member forces of a single combination are read on demand and never exported**, so a report cannot print a diagram for a combination the view does not name. One view, one diagram; a second would be a second file.
  - **Nothing reads a `@load` back into a static model's magnitude.** `validation.loads_resolve` checks that the key names a load instance and stops there; a load that *followed* the workbook the way a drawn model's does (§3.3octies) is the obvious next step and would make `@load` more than a cross-check.
  - **A support reaction is addressed by its node** (`N1`), not by the support: an RFEM support is one definition over a set of nodes, so the node is what a reaction belongs to — but a report that wants «the reaction at the left support» must know that node's number.
  - **`rfem-max` and `show-rfem-forces` cite nothing.** A solver's answer is not a clause, so the prose must cite what the model was calculated to. Whether a structure should carry the norm its combinations were built to — SIA 260's own — is a question, not an omission.

- **The RFEM import, what it does not do yet** (v0.98, §3.3duodecies). None is blocked on a decision; each is an addition.
  - **`export_rfem.py`, the accelerator.** `dlubal.api` over gRPC would write the same table export from a running RFEM with one command, so the engineer would not click through the dialog. It is not built because **it needs a Dlubal API key** (§13), so it can only ever be optional: the file stays the route, and the module would write that file and nothing else. ⚠️ **The 120 s lock** is what makes writing it delicate and is worth stating here: a script that holds the API past about two minutes locks the server, and recovering it costs an RFEM restart **and the computed results**. `app.export_to(ResultTableCsvExportAttributes)` took 167 s and did exactly that; `app.get_results(...)` takes 18 s for everything. Whatever is written must stay well inside that and never ask for a table export over the API.
  - **A stale export is not noticed.** Woodcore hashes the file it read (`source.sha256` in `data/rfem/<export>.json`), so it *could* say that the file on disk is newer than the last import — the stale-data banner the loads already have (§10quater). Three answers were put to the engineer — a banner, re-reading automatically, or nothing — and he has not chosen, so nothing is done yet.
  - **The forces reach no calculation.** They are read, checked against three other routes and written into `data/rfem/<export>.json`, and nothing consumes them: a design force in the report is still written by hand (§10quinquies). What would consume them is the load combinations (§3.5, the first item of this section), at which point a `@load` on an RFEM load case and a Woodcore load instance would be the same number read twice.
  - **A surface is read and never drawn.** `model_tables.py` reads the surfaces and `structure_detection.py` groups them, and a static model carries no area at all (§3.3octies), so a surface contributes its `@position` and nothing else. His own model has none, which is why the reader's surface half is exercised only by the fixture.
  - **The tab cannot open an export.** It lists what is in one and what is wrong with it; it does not show the model, and *Ajouter un modèle…* is the only thing it writes to the project. Drawing an imported structure in the tab would be `statics_svg` given a record it already understands — the figure exists, the tab does not ask for it.
  - **A position's section disagreement is reported and never resolved.** Member 24 is 500/200 mm in RFEM and 100/200 in `Positionen.xlsx` (§3.3duodecies): the warning names both and neither file is touched. Which of the two wins — and whether Woodcore should offer to write the workbook, which it now can (§7, v0.94) — is the engineer's.
  - **No `@` key names a load combination.** A combination is read with its cases and carried into the structure, and the report cannot address one: `show-static-model` draws a system, and which combination its loads belong to is said in the prose. That is the same boundary §3.3octies draws, met from the other side.
