# Build, export and release workflow

> woodcore-cli, the engine copy, archives, new projects, migration, installer, publishing, website.
>
> Moved verbatim from CLAUDE.md (§12) on 2026-10-07. The § numbers are kept as stable anchors: `docs/README.md` maps every § to its file.

## 12. Build workflow

**`woodcore-cli` is the build** (v0.82), and Woodcore's *Exporter PDF* is the same build in the window. Both work on one project, named by its `.woodcore` file — `--project <file>`, else `WOODCORE_PROJECT`, else the one beside the code (§11) — and both compile the project's `report` into its `pdf`: `Statischer Bericht (typst)/Statischer Rapport.typ` into `Statischer Bericht (typst)/Statischer Rapport.pdf`, **beside its `.typ`**, in the report's own folder, which is the Typst root and where Tinymist writes it by default (v0.87, the engineer: «le pdf doit être créé au root et pas un dossier au-dessus»; beside the workbooks, one level above, until then). A project whose `.woodcore` states its own `layout.pdf` keeps it, and a folder converted from the old layout states its PDF where the old build wrote it. It replaces the `build.ps1` and the `Makefile` the project folder carried until v0.82, which spelled that folder's paths and so could build that one project alone. ⚠️ **Since v0.111 a project laid out in three documents has one PDF per document**, each beside its entry file, each compiled only if its Typst changed; what this paragraph and the ones below say of the report is each document's shape, and the three documents have their own paragraphs after «What an export does».

```bash
woodcore-cli export --project Musterprojekt.woodcore                 # the report as written -> "Statischer Rapport.pdf"
woodcore-cli export --project Musterprojekt.woodcore --level 1       # force the base level for this run (overrides still apply)
woodcore-cli export --project Musterprojekt.woodcore --uniform 2     # every call at level 2, overrides ignored
woodcore-cli export --project Musterprojekt.woodcore --all-levels    # also the three uniform variants in _woodcore/out/
woodcore-cli export --project Musterprojekt.woodcore --skip-data     # compile only, against the data already exported
woodcore-cli export --project Musterprojekt.woodcore --lang fr       # the same report in French (de, fr, en -- §4bis)
woodcore-cli export --project Musterprojekt.woodcore --document cu    # one document (cu, bp, rs, or all -- the default), each compiled only if its Typst changed since its PDF (v0.111)
woodcore-cli export --project Musterprojekt.woodcore --force          # compile and archive every document asked for, changed or not
woodcore-cli check  --project Musterprojekt.woodcore                 # the whole export, writing nothing -- and a sync.json that does not read stops it, a document out of step is said, block by block (v0.117)
woodcore-cli sync status --project Musterprojekt.woodcore            # what the three documents share and where each block stands, writing nothing (v0.117, issue #33)
woodcore-cli sync share  --document cu --section accepted-risks --to bp rs   # a section shared, as «Partager» in «Structure du document»
woodcore-cli sync import --document bp --choice-all theirs      # what the others changed, taken into bp; a conflict without --choice/--choice-all is refused, nothing written
woodcore-cli sync move   --document cu --section norms --parent basics --position 0   # a section moved in its document's tree
woodcore-cli sync-engine --project Musterprojekt.woodcore            # the engine copied into the project, as an export does
woodcore-cli export --project Musterprojekt.woodcore --data-only     # the export alone, no PDF and no archive: what «Importer Excel» runs
woodcore-cli new "D:\Projekte\Halle Nord" --author "..."        # an empty folder made a new project (v0.83)
woodcore-cli new "D:\Projekte\Halle Nord" --folders "1_Nutzungsvereinbarung" "2_Projektbasis" "3_Statischer Bericht"   # the three documents' folders named (v0.111)
woodcore-cli new "D:\Projekte\Halle Nord" --style compact           # the look of the three documents, their one config.typ: neutral (the default) or compact (v0.112)
woodcore-cli migrate --project Musterprojekt.woodcore --dry-run       # what moving a project laid out as one report into three documents would do, and what stands in its way (v0.111)
woodcore-cli migrate --project Musterprojekt.woodcore                 # the migration itself, proved against a reference and undone at the first difference
woodcore-cli migrate --rollback Musterprojekt\_Archiv\migration-260930-23h54   # a migration undone on request
```

`woodcore-cli` is `Woodcore\woodcore-cli.bat`, or `python calc/cli.py`, or `woodcore-cli.exe` beside an installed Woodcore (v0.83). With neither `--level` nor `--uniform` no `--input` is passed, so the base level is the document's own (§4); the two together are refused, as the window's one exclusive group of seven entries cannot even ask for them (§10quater). The three `--input` flags are spelt once, `cli.input_args`, and the window's menu builds its flags through it.

**What an export does, in this order, and the order is the rule.** (1) The engine's copy is compared with the program's (below), before anything is read, so a refusal costs nothing. (2) `export_all.py` reads the workbooks and the sources, validates every record (§3.6) and writes `_woodcore/data/` — nothing is written if anything fails, and the command exits non-zero. (3) The engine is copied beside the export. (4) `typst compile`, only if the export passed: Typst is never compiled against unvalidated data. (5) The archive. `--skip-data` starts at (4), against the export already there; `--all-levels` then writes the three uniform variants, which are not archived.

**Three documents (v0.111).** A project whose `.woodcore` states `layout.typst_root` is written as up to three documents — `cu`, `bp`, `rs` (`project.MODES`) — and `export` compiles **each into its own PDF**, beside its entry file, and archives each apart: `--document cu|bp|rs|all` names one or all (the default; for a project laid out as one report, the report alone, which is all it has and what `export` has always meant for it), and a document the project does not have is refused naming the migration. ⚠️ **Every compile is built by `documents.compile_args(here, mode, flags, target, deps)`**, the one spelling of a compile's command line — `typst compile --root <the Typst root> <flags> [--deps <file> --deps-format json] <entry> <target>`, the entry and the target last, which `tests/test_pdf_button.py` reads — for the command line, the window, the migration and the preview phase 2's Structure tab will compile alike; until v0.111 no route passed `--root`, which was right while the root was the report's folder and is not while it is the project's. ⚠️ **A document is compiled only if its Typst changed since its PDF was written** (`calc/stamps.py`, the engineer's rule), and it is asked before anything is compiled: `cli.compile_document` calls `stamps.changed(here, mode, flags)`, and where nothing changed — the reason is an `engine.Note` with a code, the window's words being keyed by it — the document is **neither compiled nor archived** and the command says so (`woodcore-cli: <mode> (<name>) is unchanged since its PDF`); `--force` compiles it all the same. What a stamp is: every compile of a deliverable is run with `--deps`, Typst writes the path of every file it read (absolute, or from the folder it was started in, which is always the Typst root: on Linux and macOS it writes them relative, and `stamps._read_deps` reads them from there) — the sections, `config.typ`, `commands.typ`, the engine's `lib/` and the norm tables, `data/`, the pictures, and none it did not read — and after a **successful** compile `stamps.record` writes `_woodcore/stamps/<mode>.json`: the PDF's SHA-256, Typst's version, the flags and each input's digest, `sha256:` for a file of the project and `stat:<size>:<mtime_ns>` for one outside it (a font, a package), being Typst's and not the engineer's. `changed` compares today's files with it: no record, another Typst, other flags, a PDF gone or not the one written, an input missing or changed — or, where Typst's list is not there, **added** to the enumerated fallback set (the `stamp_*` codes). ⚠️ **A digest of the content and never a modification time**: a file saved again with the same bytes — NextCloud dating it, an editor saving without a change, the export writing identical JSON (`data/project.json` carries no date, which is what this section has always protected) — recompiles nothing, and the title page's date does not count. ⚠️ **An input modified after the PDF was written is not vouched for** (`unsettled`: it never matches and the next `changed` names it), `record` running after the compile, so that a file saved in between would be hashed in its new state; a time in the future is another machine's clock and is not held against a file. A deps file missing or not this compile's falls back on an enumerated set (`stamps.enumerated`: the document's folder, the shared files, `_woodcore/{lib,calc,data}` and the pictures) and the stamp says so. The preview of a document keeps a stamp of its own (`<mode>.preview.json`) and never says anything of the deliverable. Measured: `changed` 0.18 s and `record` 0.25 s, not a per-keystroke cost. `--all-levels`' variants are the report's and are not stamped; `stamps/` is gitignored (`**/_woodcore/stamps/`), the machine's own, and left out of every archive. **Exit status**: a document that does not compile fails the command, and the others are still compiled.

**Every document is archived apart (v0.111).** A project in three documents archives **each document it compiled** (`archive_export.run(route, detail, mode=…)`, `--mode`): `<timestamp>-<mode>.zip` beside `<timestamp>-<mode>-<its PDF>`, the manifest carrying `document`. The zip holds what reopens that document — the `.woodcore`, the document's own folder less its PDF, the shared `config.typ`, `commands.typ` and `references.bib`, `_woodcore/` less `out/` and `stamps/`, `Images/` (and, until the RFEM import was retired in 0.117, **`RFEM-Export/`** -- the engineer's answer: the RFEM exports were in every archive), the sources and the three journals — **chosen by name, never by walking the Typst root**, which is the whole project's folder there and would sweep in the other documents, the workbooks, the architect's plans and the archives themselves (`members_of_document`). A report alone keeps `<timestamp>.zip`, less its stamps.

**A new project is three documents (v0.111).** `project_template.create(folder, name, template, document_language, report_language, report_folder, folders, document_templates, **details)`: `folders` is `{mode: name}`, or three names in the order CU BP RS — `woodcore-cli new --folders` —, `--report-folder` names the report's alone and is refused where it contradicts `folders`, and what neither names is what `templates.folders_offered` offers, `documents.MODE_FOLDERS` for the project's language. **Everything is validated before anything is written** (`documents.modes_layout`: each folder one name, the three distinct as Windows compares them; `_check_names`: none meeting a file or a folder the project keeps at its top) and a creation that fails removes what it wrote. The report-shaped template, `templates/projet/` — which **stays report-shaped on disk** —, is copied, its report's folder renamed `3_…` and what the three share taken up to the project's folder, the paths its files write normalised (`typst_paths`); the convention and the base are made from `templates/documents/<mode>/standard/<language>/` (`doc_templates.instantiate`: the entry named after the document in the project's language, its structure block generated from its `structure.json`, never overwriting; **the full catalogue since v0.112**, 59 and 72 sections (§3.3octodecies)); the `.woodcore` states its layout in full, the languages are written into `/config.typ` and the three entries (the document's and the engine's, one choice setting both as in v0.100), and `export_all.seed` seeds the three journals. A documents-shaped template — `save_project` on a project in three documents — carries its own. `templates.REPORT_FOLDERS["en"]` is «3_Statical report»: the engineer's forms replaced the «Static report» of v0.100. Creating a project laid out as one report is no longer possible; reading, exporting and migrating one is.

**Migrating a project laid out as one report (v0.111)** — `woodcore-cli migrate`, `calc/project_migrate.py`, offered by the window as a project opens (§10quater). What it does is small and how it does it is the whole of it, because it moves the engineer's real project on disk: **nothing is deleted and nothing copied — things are renamed**. The order is the rule. (0) `plan` (pure) and `check` refuse **by name**: already three documents, no report, the report at the top of the project, the sources or the archives or the export inside the report's folder, a target that exists already (`config.typ`, `commands.typ`, `references.bib`, `Images`, `_woodcore` or one of the three folders), a path literal no rewrite can follow, a lock another window holds, an engine copy newer than the program or one to ask about without `--update-engine`, Typst or pypdf missing, no template (`already_modes no_report report_at_top sources_inside archives_inside generated_is_report bad_language bad_names collision unrewritable woodcore_unrewritable no_template locked engine_own engine_newer engine_asked no_typst no_pypdf`); `--dry-run` stops here and prints what it would do. (1) a **backup**, `_Archiv/migration-<timestamp>/before.zip` — the `.woodcore`, `.vscode/settings.json` and the whole old report folder — and a **write-ahead log**, `moves.json`, written before the first move and after every step, **both before the reference**, so that undoing the migration undoes the reference's own export and engine sync too. (2) the **reference**: unless `--skip-data` the export is run and `data/` kept; the report is compiled as it is written, its pages read as text, its outline and the variables its PDF carries kept. (3) the moves, by rename, in this order: `_woodcore`, `Images`, `config.typ`, `commands.typ` and `references.bib` up to the project's folder, and **last** the report's folder becoming `3_…`. (4) the rewrites, textual: `typst_paths.rewrite` over every `.typ` of the report — a literal written again **only where it would stop reaching its target**: `../commands.typ` becomes `/commands.typ` and `../Images/x.png` `/Images/x.png`, while `#include "Sections/…"` and `project: "references.bib"` stay as they are and every other byte is kept, line endings included —, the `.woodcore` (`project.update` where the file is in Woodcore's own form, a textual insertion where it is not: **a file written by hand is never reserialised**), and `.vscode/settings.json` gaining `"tinymist.rootPath": "${workspaceFolder}"` as a line of its own, made from the template's where the project has none. (5) the **two new documents** from their templates, and `export_all.seed`. (6) the **proof**: the project read again must be laid out in three documents with its engine current; the export run again must write the same `data/`, byte for byte (until 0.117 **the one thing allowed to differ was the path of an RFEM export that moved**, which the export recorded -- 3 491 occurrences in Musterprojekt's `rfem.json`; the RFEM import and that loosening were retired together, and `RFEM-Export/` now stays in the report's folder and moves with it); the report compiled from its new place, into its real PDF and with `--deps`, which writes its stamp, must print the same page count, the same text page by page, the same outline and the same variables modulo the runs of white and the day the title page prints; and the two new documents must compile. (7) **A failure anywhere undoes everything, automatically**: the new documents go into `rolled-back/`, every file of the old tree is restored from the zip where it differs, the renames are undone in reverse, `result.json` says why and the exception is raised; `rollback(workspace)` does the same on request (`--rollback <the migration's folder>`) and **refuses** where the engineer has changed something since — a moved path not where the log put it, a rewritten file not the bytes the migration wrote. (8) Success writes `result.json` `ok: true`, archives the report (`archive_export.run(…, mode="rs")`) and prints a reminder: open the project's folder in VS Code and pin the entry of the document being written. Every write and rename retries a `PermissionError`, NextCloud holding a file just written. **Measured**: the migration of a scratch copy of Musterprojekt with the full reference took about 60 s — `data/` identical modulo the 3 491 paths, 23 pages, 48 outline entries and 17 attachment domains identical, no page printing an RFEM path, and the rollback leaving the copy **byte-identical** (278 files); then the real one, on the engineer's go, `_Archiv/migration-260930-23h54/`. **No test migrates the engineer's project** (§11ter).

⚠️ **Tinymist and the three documents (v0.111).** A section imports `/commands.typ`, and Tinymist resolves it against **its root**, which is the folder VS Code was opened on unless `tinymist.rootPath` says otherwise. So the project's folder has to be the folder VS Code opens — «Ouvrir dans VS Code» does, starting it on the project's folder with the document's entry open — and the template's `.vscode/settings.json` (and a migrated project's) states `"tinymist.rootPath": "${workspaceFolder}"` as a safety net: Tinymist wants an **absolute** root and refuses `"."`, and the VS Code extension substitutes the variable before Tinymist reads it. Probed against Tinymist 0.15.8's own language server on a migrated copy (`tests/test_editor.py` holds the project's folder as the root its settings state): the project's folder as the root — stated or by the workspace — resolves `/commands.typ` from a section in `3_Statischer Bericht/Sections/`, and **a document's folder as the root, stated or by the workspace, answers «file not found»**, which is why the root is stated and not left to whichever folder happened to be opened. One entry is pinned at a time («Typst: Pin the main file»), the one being written, or every section compiles on its own and exports a stray PDF.

**The engine's copy** (`project.sync_engine`). Typst reads nothing outside its root, and the engine finds the export by the relative path `../data/`, so `lib/`'s files and the glossary `lib/i18n.typ` reads are copied into `_woodcore/`, beside `data/` — since v0.87 also `lib/distance.typ` and the fourteen `calc/norms/` files it reads as `../calc/norms/` (`project.ENGINE_FILES`, held equal to the files `lib/distance.typ` names by `tests/test_distance.py`) — and since v0.99 also **`lib/bibliography.typ` and `calc/norms/norms.json`**, the catalogue `#show-bibliography` names its documents from (`project.ENGINE_FILES`, held equal to the file `lib/bibliography.typ` reads by `tests/test_bibliography.py` and, with the distance and timber tables, by `tests/test_distance.py`). A project's own `references.bib` is **not** part of the engine: it is the project's, in the report's folder, written by the engineer and copied by nothing. — with a `VERSION` naming the program's version and each file's SHA-256 — which is also what lets a report compile in Tinymist with no program at all, and what makes a project carry the engine that produced its PDF. The copy is compared with the program's before it is written (`project.engine_state`): *absent* is written; *current* is left alone; *stale* — the same version, other bytes: the code run from its sources and edited since — is replaced; *older*, written by an earlier version, *unknown*, engine files no `VERSION` names (a folder laid out before Woodcore, below), and *edited*, whose files no longer match its own `VERSION`, are replaced only with `--update-engine`, or once Woodcore's dialog, which shows the difference, is answered; *newer*, written by a later program, is never replaced. The files are written read-only. ⚠️ **The export refuses all three of those up front** (`project.ASKED`, v0.87): its check before anything is read named *older* and *edited* and let *unknown* through, so such a copy let `export_all.py` write `data/` and then stop at `sync_engine`, the export and the engine parted. ⚠️ **The same comparison is made when Woodcore opens a project** (v0.87, `check_engine`, §10quater): an absent or stale copy is copied without asking, an older, unknown or edited one asked about in the very box an export asks with — «Plus tard» writing nothing and the question coming back at the next opening —, a newer one said; a project opened read-only is left alone. The command line asks nothing at opening, having no opening: its engine is compared at each export, as before. ⚠️ **Only the files a copy's `VERSION` lists are checked for edits** (v0.87): a file the engine gained since — `lib/distance.typ` and its tables — is absent from an older copy by construction, which makes the copy *older* or *stale* and not *edited*. ⚠️ **The comparison is only as good as the version number**: `project.VERSION` stayed 0.83.0 from v0.83 to v0.86, so the sources took the installed v0.83's copy for one of their own edited between builds (*stale*) rather than for an older one, and an engineer working with the installed program met, as missing, commands the sources had had for three versions. It is **0.87.0** since v0.87, and both real projects had their engine replaced (`woodcore-cli sync-engine --update`) and their Tinymist setting brought to the new PDF place; a version is bumped with every release from now on (§13).

**`data/project.json` names what produced the export** (`project.record`, `schemas/project.schema.json`): the project's name and details as its `.woodcore` states them, Woodcore's version and, from a checkout, `git describe --always --dirty`, Typst's version, and the SHA-256 of every workbook the export read. It carries **no date**: an export that changes nothing leaves it unchanged to the byte, which keeps `data/` comparable from one export to the next; the date is the archive's. `project-info()` reads it for the title page, and `#show: woodcore-document` in `Statischer Rapport.typ` gives the PDF its title, author and keywords from it (§10bis).

**Every successful export is archived** (`calc/tools/archive_export.py`, v0.71, one zip since v0.82), in the project's `_Archiv/`: `<timestamp>-Statischer Rapport.pdf`, a flat copy to look at, and `<timestamp>.zip`, holding the `.woodcore` file, the report's folder — the report, its sections and pictures, the export and the engine's copy, **but not the PDF**, which lies in that folder since v0.87 and whose copy already stands beside the zip: a zip holds the state that produced the PDF, not the PDF a second time — and Woodcore's sources, with `archive-info.json` naming the route, the `--input` flags and `project.json`. The workbooks are not in it: they are the engineer's, and `project.json` records their hashes. The timestamp is `AAMMJJ-HHhMM`, a second export in the same minute told apart by `-2`, never overwriting the first. Archiving is a convenience and never part of the validated pipeline (§3.6): a failure — a full disk, a slow sync — warns and never fails a build that has already produced its PDF. Tinymist's on-save export is not archived. The manifest's route is `woodcore-cli` or `gui` (v0.96, `archive_export.ROUTES`); `katalog`, what a window older than v0.96 passes, is accepted and recorded as `gui` (`LEGACY_ROUTES`).

**Tinymist** writes the same PDF: its default output, `$dir/$name`, is beside the `.typ`, which is where the build writes it since v0.87, so the project's `.vscode/settings.json` sets **no** `tinymist.outputPath` — until v0.87 it set `"$dir/../$name"`, one level above; a project whose `.woodcore` names another `layout.pdf` sets `outputPath` to match it. `Statischer Rapport.typ` is pinned as the main file once (command palette → *Typst: Pin the main file*), or each section compiles alone and exports a stray PDF.

**Sharing from a terminal: `woodcore-cli sync`** (v0.117, issue #33, `calc/cli_sync.py`). Sharing, importing and moving a section between the convention, the base de projet and the report were the «Structure du document» tab's alone. `sync status | share | import | move` does them from a terminal with the domain functions the tab calls -- `sync.status` (read with `settle=False`: a status writes nothing), `sharing.share`, `sync.import_changes`, `structure.move_node` -- and decides nothing itself, so a command writes the files the tab's action writes, byte for byte (`tests/test_cli_sync.py`, on copies of `tests/projet-exemple/`). **A conflict is never settled by default**: `import_changes` given no items imports what is incoming and leaves a conflict as it stands, right for the tab, which asked first, and wrong for a terminal, where a partial import would pass for a whole one; so `import` reads the status first and refuses, before writing anything and with exit code 1, every conflict that no `--choice <item>=mine|theirs|cu|bp|rs` and no `--choice-all <choice>` settles, listing them -- never a question, a script having no keyboard. A refusal of the domain is said with its code (`already_shared`, `needs_choice`, `no_such_node` …) and its English sentence, exit 1. **Its words are the only ones of woodcore-cli in three languages** (`calc/i18n/cli.json`, `--lang`, by default the language of the project's documents), the engineer's choice (spec D-15); every other command speaks English, like the pipeline. **`check`** adds what it says of the records: a `sync.json` that does not read stops it, naming the file and the field (exit 1), and a document with incoming changes or conflicts is a warning naming the command that shows them -- read, never settled. The command is `sync`; the copy of the engine into a project stays `sync-engine` (its function in `cli.py` renamed `sync_engine`).

**A new project** (`woodcore-cli new <folder>`, the start page's and the *Fichier* menu's *Nouveau projet*, `calc/project_template.py`, v0.83) is `templates/projet/` copied into an empty folder: `Statischer Bericht (typst)/` — the entry file of every report, `config.typ`, `commands.typ`, and seven sections that loop over what the export holds (`plan-ids`, `position-ids`, `connector-ids`, the cases of the three load domains, `static-model-ids`), so a plan, a load or a model drawn reaches the report with no edit — `.vscode/settings.json` for Tinymist, the folders of `Woodcore-Datei/`, `Images/` and `_Archiv/`, and a `Positionen.xlsx` holding the headers the export reads, written by openpyxl from `POSITION_COLUMNS` — held equal to `export_all.py`'s by a test — with the STE legend of `plan.TYPES` on its `data_type` sheet; then the `.woodcore`, and the engine copied beside the export-to-be. Since v0.99 the report skeleton also carries a **`references.bib`** of comments alone, and `Sections/007-literatur.typ` names it with `project:` — so a new project's bibliography works from its first compile and the file is discoverable. ⚠️ The file may be emptied but not deleted while the section names it: Typst's `read()` on a file that is not there is a report that does not compile, and there is no way to ask whether a file exists. Both the file and the section say so. ⚠️ **No load workbook is made**: the office's is a `Belastungsannahmen` template, whose macros and controls openpyxl cannot write, and until a workbook is copied in the export goes on without loads (§3.3, v0.89.1; a blocking error until then) -- with a warning until v0.116, one line of information since v0.117. ⚠️ **The report compiles from the moment the project exists** (v0.86.1), and not from its first export as until then: `export_all.seed` writes the export of a project holding nothing yet — `project.json` for the title page, and `positions-index.json`, `calculations.json` (SIA 261 Tabelle 8's live loads alone, which need no workbook), `connectors.json`, `connections.json`, `plans.json`, `statics.json` and `schemas.json`, each empty — **each only where it is missing**, so an export or a save in Woodcore is never overwritten. It runs when a project is created and when the window opens a project it may write to, which is what repaired the projects made before it: the first one *Nouveau projet* made stopped Tinymist on «file not found … data/project.json», its report reading six files of an export a project without a load workbook cannot run.

**A project from a template (v0.94).** ⚠️ Since v0.114 the project template is dissolved into a layout template and three content templates (the paragraph after the next). A new project is made from a template (§10quater's *Paramètres*): «Standard», which is `templates/projet/` with a `template.json`, the user's own, or an office's shared one — «Nouveau projet» offering the default first, `woodcore-cli new --template <name>` naming one, else the default the settings name, else Standard (`project_template.create(folder, name, template=None, document_language=None, report_language=None, **details)`). A template's languages are written into the files it copies — `config.typ`'s `doc-lang`, the entry file's `set-report-language` default —, its folder names into the `.woodcore`'s `layout`, and its author, office and checker into the project's details where the dialog was left empty; the languages and the people fall back on the settings', then on German. The template's `Positionen.xlsx` carries the `section type` column after the strength class, its list on `data_type` and a drop-down refusing anything else, beside the type's own drop-down (§7). ⚠️ A template that moves the PDF does not adjust Tinymist's `outputPath` (§14).

**The installed program** (`packaging/`, v0.83) is built on demand, never on every change — the engineer works from the sources, and a build is a version handed to someone or kept — and since v0.87 **once per version by itself**, a commit that changes `VERSION` starting the build of its installer (below):

```bash
python packaging/build.py                                        # the program, the launcher, checked, then the installer
python packaging/build.py --compare ..\Musterprojekt\Musterprojekt.woodcore  # and that project's data/ from the sources and from the built program, compared
python packaging/build.py --installer-only                       # the installer alone, from the program the last build left: what an edit to woodcore.iss needs
```

`build.py` runs in an environment of its own, `%LOCALAPPDATA%\Woodcore\build\venv`, holding `requirements.txt` and `packaging/requirements-build.txt` (PyInstaller) and nothing else, which it creates the first time; it refuses to build where the packages are not the pinned ones or `typst --version` is not the one requirements.txt names. It writes `build-info.json` — the version (`project.VERSION`, **0.87.0** since v0.87, 0.83.0 from v0.83 to v0.86), `git describe --always --dirty` of the sources, the date, Python's and Typst's versions —, which an installed program reports in `data/project.json` where a checkout reports git (`project.source_revision`). PyInstaller builds **`woodcore.spec`**: `Woodcore.exe` (the window) and `woodcore-cli.exe` (the command line) in one folder, with `typst.exe` inside it, which `project.typst_executable` takes over the PATH's once frozen. ⚠️ **The program's own modules are not frozen into PyInstaller's archive**: they are shipped as they are, under `_internal/calc/`, and the two entry points (`entry_gui.py`, `entry_cli.py`) import them from there, compiled once at the build. Every path a module derives from its own file — a norm's JSON beside its reader, the glossary beside `strings.py`, the schemas beside `calc/`, the examples — is then the path it has in the checkout, and `domains`, `norms` and `i18n`, packages without an `__init__.py`, import as they do from the sources; what `calc/` imports from outside is read off every import statement it holds, those inside a function included, and handed to PyInstaller as hidden imports. `lib/`, `schemas/`, `examples/` and `templates/` travel beside them. The window's *Importer Excel* runs `woodcore-cli.exe export --data-only` beside it; `dependencies.py` and pip are not asked. **`launcher.spec`** builds `Woodcore-Launcher.exe`, one file of standard library. Then the build **runs** what it built: `woodcore-cli.exe` copies the engine into a copy of the example project, compiles its report with its own Typst and archives it, the PDF looked for where that project's `report_pdf` says (v0.87, rather than at a fixed place); `Woodcore.exe --self-test` opens it and quits (0 where it opened); the launcher picks the version of a profile of its own (`--dry-run`); and with `--compare` a copy of a real project is exported by the sources and by `woodcore-cli.exe`, and the two `data/` must be identical to the byte — on Musterprojekt, 37 files, identical. Only what is handed over lands in `Woodcore\dist\`, which git ignores: with Inno Setup 6 installed (`ISCC.exe`), `Woodcore-<version>-setup.exe`; without it, `Woodcore-<version>-win64.zip`, the folder as it is.

**The installer** (`packaging/woodcore.iss`) installs **per user and without administrator rights** into `%LOCALAPPDATA%\Programs\Woodcore\<version>\`, each version an installation of its own — its own AppId, its own entry among the installed programs, its own uninstaller — so several stand side by side and a project exported years ago opens again with the program that exported it. Beside them, in `launcher\`, it puts `Woodcore-Launcher.exe` and `woodcore.ico`, a Start menu entry «Woodcore» on the launcher and one per version, and — a task the engineer may untick — the `.woodcore` association, in `HKCU\Software\Classes`, on the launcher. A version's installer replaces the launcher only with a newer one (its version resource), and the last version uninstalled takes the launcher, the entry and the association with it. **The launcher** (`packaging/launcher.py`) starts, for a `.woodcore` double-clicked: the engineer's own sources where the settings say so (`launcher.dev_checkout`, set from the *Fichier* menu of a window run from the sources); else the version the project asks for (`woodcore_version`), the newest installed whose number begins with it; else the newest installed — unless the project's engine was written by a newer version than any installed, which would refuse to write into it, and which the launcher says itself. Started without a file, it opens the newest version's start page. ⚠️ **An unsigned executable** meets SmartScreen the first time it runs, and possibly an office's antivirus or policy: to be tried on an office machine before it is handed round (§14). From the sources it starts `calc/tools/woodcore_gui.py`, falling back to `catalog_gui.py` for a checkout older than v0.96 (`launcher.GUI_SCRIPTS`).

**The installer is rebuilt at each new version** (v0.87, second half, the engineer: «L'installateur devrait également automatiquement être reconstruit à chaque nouvelle version»; `packaging/auto_build.py`, `packaging/hooks/post-commit`). A git **`post-commit` hook** — a shell script, kept LF by `packaging/hooks/.gitattributes`, since `sh` checked out with CRLF would read `exit 0` as `exit 0\r` — is activated on a clone with `python packaging/auto_build.py install`, which is `git config core.hooksPath packaging/hooks` and refuses where it would silence hooks the clone has of its own (`--force` does it all the same); `uninstall` unsets it, and `status` says whether it is active, whether a build runs and whether HEAD's installer is in `dist/`. It is active on the engineer's clone, where `.git/hooks/` held only git's samples. **What fires a build**: after every commit the hook asks git first and starts no Python at all unless `calc/project.py` differs from the commit's first parent; `auto_build.py hook` then builds only where `VERSION` changed — a first commit carrying one counts as a change, a merge is compared with the branch it was merged into — and where `dist/` holds no `Woodcore-<version>-setup.exe`, a zip alone not counting. `WOODCORE_NO_AUTOBUILD=1 git commit …` skips it for one commit.

**Never in the commit's way, and never the working tree.** git ignores what a post-commit hook returns, and every way out of this one exits 0; the build is started **detached** — a process of its own, in a new process group with a hidden console so that neither PyInstaller, Typst nor Inno Setup flashes a window, with none of the hook's handles, and out of its parent's job where the job lets it go — so the hook returns in about 0.3 s, 0.87 s when it starts a build, and neither git nor a terminal capturing the commit's output waits the eight minutes of a build. **What is built is the commit**: several sessions edit the working tree at once, and a build of it would freeze whatever they had half written, so the commit is checked out with `git worktree add --detach <commit>` under `%LOCALAPPDATA%\Woodcore\build\checkout\` — outside NextCloud, and never the main working tree, which is refused by name — and that commit's own `packaging/build.py` builds it there, every `GIT_*` variable dropped first (inherited from the hook, `GIT_INDEX_FILE` made the checkout fail). The installer is copied into the real `dist/` only on success, never half-copied under the name the next build looks for, and the worktree is removed either way. The log is `dist/build-<version>.log`, written as the build runs and ending on what became of it; a failure before that log exists is written to `%LOCALAPPDATA%\Woodcore\build\auto-build-error.log`.

**One build at a time, and none lost.** `build.py` holds a lock, `%LOCALAPPDATA%\Woodcore\build\build.lock`, for as long as it runs, so a second build — one run by hand included — refuses while another runs, and a lock left by a build that no longer runs is taken over. The builds `auto_build.py` starts queue behind one another (`auto-build.lock`, a lock the operating system holds on an open file, waited on up to four hours): a second version committed while one builds waits its turn, says so on its log, and then looks again whether its installer is still needed. An amend therefore rebuilds nothing, the installer being there by then — `python packaging/auto_build.py start --force` replaces it, and `start [REV]` builds HEAD, or REV, by hand, in the background as the hook does. In a clean checkout `build.py` generates `examples/lib/` and `examples/commands.typ`, which are not tracked (§10sexies); run by hand from the working tree it behaves as before, and builds the tree as it stands, uncommitted edits included. ⚠️ **Only committed files are built**, so a version's commit must carry its new files: a module left untracked is missing from the installer however well the working tree runs. ⚠️ The build takes `python` and `typst` from the PATH, and the first build run outside Claude's sessions, whose `%LOCALAPPDATA%` is redirected, creates its environment in the real one — some 250 MB downloaded once more; on a clone for another system, `git add --chmod=+x packaging/hooks/post-commit` makes the hook executable.
