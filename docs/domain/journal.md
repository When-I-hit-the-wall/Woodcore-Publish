# The revision journal

> One journal per document, written by hand in Woodcore, printed by show-journal.
>
> Moved verbatim from CLAUDE.md (§3.3terdecies) on 2026-10-07. The § numbers are kept as stable anchors: `docs/README.md` maps every § to its file.

### 3.3terdecies The report's revision journal: written in Woodcore, printed by Typst (v0.99)

A **journal** is the list of the report's revisions: one entry per revision, carrying its number, the day, who made it and the office's short form, then what it is — a label, a short description and a long one. The engineer asked for it in those words («avoir un module qui permet d'enregistrer dans un journal les modifications qui ont été faites (date, nom de la personne, nom court de l'entreprise (e.g. FLL), label, description courte, description longue)»), and for the three levels to govern those three texts alone: level 1 the label, level 2 the label and the short description, level 3 everything an entry carries.

**Source.** `Woodcore-Datei/journal.json`, written by Woodcore's «Journal» tab (§10quater) and read by `calc/journal.py` alone — the arrangement the static models, the detail schemas and the position plans already have, for the same reasons (§13). `schemas/journal-source.schema.json` states its shape (`schema_version` 1.0). Two things are different from every other source, and both because a journal is one list rather than a set of named objects:

- **One file, not one per entry.** A journal is read as a whole and nothing addresses one revision by an id: no `show-*` call names one, no other source refers to one. So there is no folder of files, no `group` and no id to keep in step with a file name, and `source_paths`/`read_source` have nothing to do here. The file is the project's `journal_file` (`calc/project.py`), beside the folders of the drawings.
- **Written by hand, one entry per revision** (the engineer's decision). Nothing appends an entry when a drawing is saved: an afternoon in the schemas tab would leave twenty of them, and «what I changed in the report» is not «which files I touched».

An entry carries `index`, `date`, `name`, `initials`, `label` — all required — and `summary` and `description`, which may be absent or empty. **Required is what a revision cannot be without**: a number, a day, somebody who signs it, the office's short form, and the label, which is the whole of level 1. The two descriptions are level 2 and level 3, and an entry whose label says it all («Erstausgabe») has neither — the report then prints the label alone rather than an empty cell.

- **`index`** is the revision's number, as a drawing's revision block numbers one. Unique in the file; Woodcore proposes the largest plus one (`journal.next_index`), so **a gap is never refilled** — Rev. 2 deleted out of 1, 2, 3 leaves 2 unused and the next revision is 4 — which is `positions_workbook.propose_id`'s own rule for a position's id. The newest deleted gives its number back, which is right for one typed by mistake and taken out at once.
- **`date`** is ISO (`2026-09-27`), typed and deliberately not taken from the clock: a revision is dated by the day it was decided. Its shape is checked (`journal.parse_date`), and `2026-02-30` is refused.
- **`initials`** is typed at every entry rather than read from a setting (the engineer's decision): a journal may carry entries by several offices. Woodcore prefills it, and the name, from the entry before it — a convenience, not a setting. At most 12 characters (`journal.INITIALS_MAX`), which is a guard against a full name typed into the wrong field and then printed in a column three characters wide.

**Nothing is computed.** The export is the source's entries sorted, and that is all: there is deliberately no `{vars, steps, checks}` record, so nothing addresses a journal with `show-calc` and nobody can mistake it for a traced calculation — the rule a static model and a detail schema already follow (§3.3octies, §3.3decies).

**Export.** `journal.prepare()` reads and checks the file; `journal.write()` writes `data/journal.json` (schema `journal` 1.0, checked by `validation.validate_journal_business`). A source that is absent is an **empty journal and never an error**: a project that has never been revised exports without one, the way a project with no load workbook is a warning (§3.3, v0.89.1). `export_all.seed` writes an empty one, so a new project's `Sections/008-journal.typ` compiles from the moment the project exists (v0.86.1's rule).

**The entries are exported newest first** (the engineer's decision), ordered by the **index and never by the date**: the date is typed, so it may be wrong or two entries may share one, and a journal that reordered itself around a typo would print a revision under the wrong one. `validate_journal_business` holds that order rather than trusting it — `show-journal` prints what it is given and never sorts, and `journal.latest`, which the PDF's keywords name, is simply the first entry.

**The PDF's metadata carry the latest revision** (the engineer's decision): `data/project.json` gains an optional `revision` — `{index, date, label, initials}` — passed to `project.record()` by `export_all` rather than read there, so `project.py` knows nothing of the journal and `seed()` writes a record without one. `woodcore-document` adds the keyword «Rev. 3 (2026-09-25)» beside the Woodcore and Typst versions, so two PDFs of one project can be told apart by their properties and not only by their pages. It is read from `project.json` and **not** from `journal.json`: a `set document` rule stands at the top of a document and cannot ask whether a file is there, so a second `json()` there would stop every report of a project whose engine was updated without being exported again. Its date is the engineer's typed day, so an unchanged journal still writes the same bytes (§12's own rule).

**In Typst.** `show-journal(form:, level:, title:)` and `journal-entries()` (§10bis). The three forms are the engineer's own list:

| form | what it sets |
|---|---|
| `"table"` | Rev. · date · name · short form · the texts, through `render-table` — three rules and nothing else, a column aligned by what it holds (§3.3) |
| `"list"` | one block per revision: `Rev. 3 — 25.09.2026 — PPA — Petra Prüfer: **label**: short description`, the long description a paragraph of its own |
| `"grid"` | cards, several to a line as the start page sets its recent projects: three at level 1, two where there is prose to read |

⚠️ **What the level governs is the three texts and nothing else.** The revision's number, its day, the name and the short form identify it and are printed at every level — a table is a table, and its levels change what its columns carry rather than which entries it has.

⚠️ **In the table, every text column shares the leftover width** (`wide`, which is `1fr`) as soon as there is more than one of them; at level 1, where the label is the only one, none does and the table is measured and centred in the calculation's own column. Sized by their own text (`text`, which is `auto`) they do not fit: at level 3 the label column took the width its longest label wanted and the two descriptions were left with less than their own headings, and the table ran off the page.

⚠️ **And a narrow prose column is hyphenated**, which is the one place this engine asks for it: a table's cells are set ragged (`render-table`), and Typst's `hyphenate: auto` hyphenates only what it justifies — so in a column three centimetres wide a German compound («Verbindungsmittel», «Kurzbeschreibung») ran past its column's edge. It is set in `show-journal` and nowhere else, so no other table of the report changes; a revision block on paper is hyphenated for exactly this reason. Measured rather than assumed: `#context text.hyphenate` reads `auto` on either side of a `#show-journal` call, the `set` rule staying inside the command's own `context`.

⚠️ **The engineer's three texts are never translated** (his decision, §4bis), and that is made structural rather than probable: they go into the table as **content**, which `render-table` passes through untouched (`table-cell`, a branch added in v0.99, additive). A string still goes through the glossary, which is what every table read from the data needs. Free text is the one case where the glossary's own rule — translate it if the glossary carries it — can go wrong: a template matches on the literal segments around its holes, so a revision labelled «Element 3 ergänzt» would match «Element {n}» and a French report would print «élément 3 ergänzt» (the risk §14 records for `tl-of`). The **column headings** are the engine's words and are in `calc/i18n/strings.json` (`journal.index` … `journal.empty`), in three languages.

⚠️ **A date is printed `27.09.2026` in every language**, the report's own convention and not the language's: the title page already prints `[day].[month].[year]` whatever the report is written in, so a date is one less thing to translate and reads the way the page the reader already has reads.

⚠️ **An empty journal prints one line saying so** («Noch keine Revision erfasst.»), rather than nothing at all: silence would read as a command that did nothing.

**The archive holds it.** `archive_export.members()` walked `project.SOURCE_FOLDERS`, the five **folders** of the sources, so a file at the top of `Woodcore-Datei/` reached no archive: the journal is added by name (v0.99). An archive is what reopens Woodcore on exactly the state a PDF was produced from (§12), and the journal is what the report's own page prints — without it that page could not be reproduced. `tests/test_archive.py` holds it, and fails naming the file when the line is taken out.

**The report's own page.** `templates/projet/Statischer Bericht (typst)/Sections/008-journal.typ`, included last by the entry file — the engineer's decision that the journal has a page of its own. It is after the literature because inserting it earlier would renumber six sections of every template; the sections editor of *Fichier → Paramètres…* moves it forward in one click (§10quater, v0.94).

**One journal per document (v0.111).** A project in three documents has three journals — the engineer's decision: each document prints its own «Historique des versions», and a revision of the convention is not a revision of the statical report. The sources lie side by side in `Woodcore-Datei/`: `journal.json` for the report, as it has been since v0.99, and `journal-cu.json` and `journal-bp.json` (`project.JOURNAL_FILES`, `Project.journal_file_for(mode)`, a document the project does not have refused, a report alone having the report's); their exports are `data/journal.json`, `data/journal-cu.json` and `data/journal-bp.json` (`journal.EXPORT_FILES`; `journal.write(data, data_dir, mode)` and `journal.export(path, data_dir, mode)` take the document). The three names are written in three places — `project.JOURNAL_FILES`, `journal.EXPORT_FILES` and `lib/calc-engine.typ`'s `journal-files` — and `tests/test_journal.py` holds them equal. ⚠️ **Every export writes all of them, empty where a document has no entry** (`export_all.run`, and `export_all.seed` for a project that holds nothing yet): Typst cannot ask whether a file exists, so a convention or a base de projet compiled against a `data/` without its journal stops on the missing file, exactly as a report stops on a `journal.json` that is not there (v0.86.1's rule). ⚠️ **Which journal `show-journal` prints is the document being compiled**: each entry file says once which document it is, `#show: woodcore-document.with(document: "cu")`, which records it in a state (`wc-document`, key `woodcore-document-id`, default `"rs"` — so a report that says nothing, every probe of the test suite and every worked example are to the byte what they were), and `show-journal` reads it in its own `context`; the state is read from what the previous layout pass recorded, so the first pass of a convention still says «rs», harmlessly, every journal existing. `journal-entries(document: "rs")` defaults to the report's and **not** to `auto`, because a function that returns an array cannot ask a state; `#context journal-entries(document: auto)` follows the document. ⚠️ **The PDF's keyword «Rev. 3 (…)» is each document's own**: the report's is read from `data/project.json` as before, a convention's and a base's from their own journal's first entry — a revision of another document in `project.json` would make the report look changed every time the convention is, and the export-only-if-changed rule (§12) would compile it for nothing. The Journal tab follows the drop-down and edits the journal of the document shown (§10quater).
