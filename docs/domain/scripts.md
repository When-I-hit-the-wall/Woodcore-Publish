### 3.3sexdecies A script of the project: Python the engineer writes, run by Woodcore, whose named results the report reads (v0.100)

The engineer asked for «un onglet dans woodcore, où le user peut écrire du code python et le run», to solve an equation or a system of them — and of the three ways a result could reach the report he chose the one that keeps it **traceable**: the script declares its results, they are exported, and the report reads one by name. Nothing is copied by hand, and every value carries the source that produced it (§2 rule 5).

**Source.** `Woodcore-Datei/scripts/<id>.py`, one script per file, the id being the file name — the arrangement every other thing Woodcore's window writes has (§3.3quinquies, §3.3decies), and read by `calc/domains/script.py` alone. Its identity is three `@` comment keys at the top — `@name`, `@label` (its description), `@group` (the folder of the tab's left pane) — which is the convention an RFEM comment already uses (§3.3duodecies); ⚠️ and here the sigil is `@` **because `#` is Python's own comment marker**, so a `#name` line would be indistinguishable from prose. Everything else in the file is Python. There is deliberately **no JSON beside it**: a script's identity is in the file the engineer edits, and a form beside it would be a second place for one thing (§2 rule 1) and a round-trip to keep right — which is why Woodcore's tab shows those three read-only (§10quater).

**What a script is given, and nothing else** (`calc/domains/script_runner.py`):

| | |
|---|---|
| `result(name, value, unit="", symbol=None, label=None, descr=None, norm=None, norm_ref="")` | declares a value the report may read. The one thing a script writes |
| `value(domain, instance, name)` | a number out of the export — a load, a connector's resistance, a connection's polar moment: what `var-of` reads in Typst, read here instead, so a script computes with the project's own numbers and not with numbers retyped into it |
| `PROJECT`, `DATA` | the project's folder and its export, as `pathlib.Path`, to read whatever else it needs |
| `numpy` | pinned in `requirements.txt` and frozen into the installed program, imported by the script itself |

⚠️ **numpy alone, and not SciPy**, which is the engineer's own choice between the two put to him: `numpy.linalg` solves any linear system, which is most of what a static calculation asks for, and a non-linear equation is solved by Newton or bisection written out — where SciPy would have taken the installer from 63 MB to some 130 and left no room beside the site on Pages' 100 MB (§12, §13).

**Read-only on the project, and its own results.** `builtins.open` and `io.open` are replaced in the child by one that refuses a write mode and **names the file it refused**; they are the same function underneath, so this also covers `Path.open`, `Path.write_text` and `Path.write_bytes`. ⚠️ **It is a guard against an accident and not a sandbox**, and it is documented as that rather than promised as safety: `os.open`, `shutil`, `subprocess` and a C extension all get round it. What it catches is the stray `open(..., "w")` inside the project, which is the mistake that actually happens.

**It runs in a process of its own**, never in the window's: a script that loops for ever, exhausts the memory or segfaults must not take Woodcore with it, which is the reason the export runs in its own process too. The child is `woodcore-cli run-script <source> --report <file>`, so an installed Woodcore — which carries no `python.exe` to spawn — relaunches itself exactly as «Import données» does (`project.cli_command`). A run is bounded by `script.TIMEOUT` (60 s): a bad loop is caught with its reason rather than waited out.

**Every export runs every script**, as every other domain is recalculated at every export — which is what keeps the number in the report the number the current data gives (§2 rule 1). ⚠️ A script that fails, is given up on or declares nothing is a **warning and never a stop** (the v0.33 rule): its record carries `calculated: false` and the reason, the report refuses to print what it names, and the rest of the export goes through. The warning is an `engine.Note` (`script_failed`), so the window writes it in its own language (§4bis).

**Export.** `data/scripts.json`, `schema_version` 1.0 (`schemas/scripts.schema.json`, checked by `validation.validate_scripts_business`): one entry per script, carrying its identity, whether it ran, and the `{vars, steps, checks, results}` shape every calculation of this engine has (§2 rule 2) — `steps` and `checks` always empty, a script declaring values and not a working. A result's `source` is `python:scripts/<id>.py`, the provenance convention `domains/dead_load.py` already follows. ⚠️ **How long the run took is deliberately not exported**, though `run` reports it and the tab's status line shows it: a wall-clock duration differs at every export, and `data/` must stay unchanged to the byte when nothing else changed (§12) — which is the very reason `data/project.json` carries no date. Exporting it broke `test_export.test_the_export_is_reproducible` the moment the example project carried a script, and `tests/test_script.py` now holds that the field is absent. ⚠️ **`norm` and `norm_ref` are `""` where the script cites nothing**, and that is a decision rather than an omission: what a script computes is the engineer's own arithmetic, so its provenance is the file that produced it and there is no normative citation to invent (§2 rule 7 concerns a *step*, and a script declares no step). A report that wants one states it at the call — `#val(..., norm: "SIA 265")` — which is what `val`'s own override is for (v0.85.2). They are always *written*, because `get-norm(v)` is a plain field access in Typst.

**In Typst.** No new command at all, which is the property the engineer's choice of «named values» bought: `#val("H_d", domain: ("script", "portique"))` prints one, `#show-calc("script", "portique")` the record entire, `#find(object: "variable", domain: ("script", "portique"))` lists them. What was added to `lib/calc-engine.typ` is the `script` branch of `find-calculation` — the connector's own shape, refusing a record whose `calculated` is false with its reason — beside `script-ids()` (§10bis) and the three companions every domain of its own file needs: a line in `instance-ids`, the domain in that function's assert message, and `and domain != script-domain` in `resolve-source`'s guard, without which a script whose id looked like a position's would be scope-checked against the enclosing `calc-block`.
