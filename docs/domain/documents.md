### 3.3octodecies The three documents: sections, objects, and what they share (v0.112)

A project written as three documents (v0.111, §12) holds, for the convention d'utilisation (CU) and the base de projet (BP), **one `.typ` file for each lowest-level section** and a `structure.json` that says which are printed and in which order; the report (RS) keeps its sections as it had them. This is what is written inside those files and what Woodcore does with it: the **tags** that let it find a heading, a paragraph or a table and write it again (`calc/typst_objects.py`), the **eleven commands** that print them (`lib/document.typ`), the **sharing** of a section between documents and the **synchronisation** of what they share (`calc/sharing.py`, `calc/sync.py`), the **import** of content from another document (`calc/doc_import.py`), the **preview** of what is chosen (`calc/structure_preview.py`), and the **content templates** — a convention and a base written out in three languages — a document is made from. The window that edits all of it is §10quater's «Structure du document» tab, and **it is the only editor**: no Typst code is shown in Woodcore (§13).

### A document's structure (`calc/structure.py`)

**CU and BP**: an entry `.typ` named after the document in the project's language, a `structure.json` beside it and `Sections/<id>.typ`, the id **English, stable and without a number** (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, unique in the document, never changed by a rename — it names the file and every call that refers to the section). The structure is a tree at most four levels deep: a **group** (a chapter) has a title in the three languages, printed in the document's own, and children, and no file; a **leaf** is a section — its file is `Sections/<id>.typ`, its title the first heading of that file, and `shared_with` names the documents it is shared with. `enabled` is the flag the tab's check box sets: a disabled section **keeps its file** and is simply not included, and a disabled group takes its subtree with it. The entry file's `#include` lines between `// woodcore:structure …` and `// woodcore:/structure` are **generated** from the structure (`structure.sync_entry`) and nothing outside those two lines is touched, line endings included: a group at depth d is `#heading(level: d, "Title")`, a leaf `#{ set heading(offset: d - 1); include "Sections/<id>.typ" }`, so that a file writes its own heading as a plain `=` and is **independent of where it is included** — a section moved under another chapter, or shared into a document that nests it differently, is not edited — and a disabled one a comment, `// disabled: <id> (<file>)`. **The report has no `structure.json`**: its sections are numbered files included by `#include` lines, its order and its state live in those lines (`templates.sync_includes`), and one file may hold several headings; nesting and chapters it has no way to say.

`structure.tree(here, mode)` gives the document as a list of `Node`s in document order: a `group`, a `file` (a section, marked as a `.typ` of its own) and — **new in v0.112** — under a file that carries object tags **each of its objects** (`kind: "object"`, id `<file id>/<object id>`, with its type, a short label, the lines of its two tags, its state and the shared block it stands in); a file with no tags keeps its headings as nested `heading` nodes (`<file id>#<n>`). Every node carries the absolute level it is printed at, whether it is printed (`active`: enabled, and every chapter above it), the documents its file is shared with and what is wrong with its file. The operations that write a structure — `set_enabled`, `set_title`, `add_section`, `add_group`, `remove_section` (a section is **never deleted**: its file goes to `Sections/archives/<yymmdd-hhmmss>-<id>.typ`, and the report's include line becomes a `// archived:` comment), `move_node`, `rename_section` (refused where the section is shared: a shared section keeps its id) and `tag_section` — each validate everything first, write `structure.json`, the files and the entry file together, each beside itself and moved into place, **put back what they had written if a later write fails**, keep every file's line endings and refuse by one of twenty-two codes (`structure.CODES`), which the window says in its own words. `structure.align` maps the nodes to the bookmarks of a compiled PDF in document order, by level and normalised title, and `bookmarks_from_pdf` reads them.

### The tags, and every heading and paragraph an object (`calc/typst_objects.py`)

Woodcore finds what it edits by **tags**: a line comment, alone on its line, with the exact prefix `// woodcore:` — `// woodcore:object <type> <id>` … `// woodcore:/object <id>` around one **object**, and `// woodcore:shared <shared-id>` … `// woodcore:/shared <shared-id>` around a **shared block**. Being comments they print nothing, so a document compiles and prints as it did without them; `structure.scan_tags`, `pair_tags` and `check_tags` are **the one reader of them**, and a file whose tags cannot be read — an unclosed tag, a closing one that does not match, a block where it may not stand, an id used twice — is one **Woodcore's editors refuse to rewrite**, said by name and left for VS Code. An object's type is one of twelve (`typst_objects.OBJECT_TYPES`): ten are one call of `lib/document.typ` — `doc-table`, `live-load-table`, `dead-load-table`, `doc-field`, `doc-checklist`, `doc-choice`, `doc-image`, `doc-plan`, `doc-signatures`, `show-norm-list` — and two are **markup**, a `heading` (`= Titel`, any level) and a `text` (one paragraph: its lines, no blank line between them). An object may stand inside a shared block but not straddle it; shared blocks do not nest; the same shared id in two documents is one block.

⚠️ **Every heading and every paragraph of a CU or a BP is an object** — the engineer's rework of 01.10.2026; the first build tagged tables alone, and a heading had nowhere to be moved or shared from. The templates are written so (`typst_objects.tag_file(text, ids="plain")`: the id `title` for the file's first heading, `h2`, `h3` … for the others and `p1`, `p2` … for the paragraphs, **the same in the three languages**, so that a shared section has the same ids in both documents), and the import line, the journal's `#show-journal()` and every other line of code are not paragraphs and stay as they are. **The report's own files are not tagged by themselves**: a file that has none shows its headings in the tree, and «Baliser ce fichier» (`structure.tag_section`, `tag_file(text, ids="slug")`) wraps its untagged headings and paragraphs on the engineer's request — every byte outside the inserted lines kept, line endings and a last line with no ending included, a second run changing nothing, and what no model can be made of (a call that stands alone on its lines, an `#if` printing a heading, a raw block) left alone. A paragraph is edited in Woodcore **as the markup it is written in**, in a plain text box with no syntax colours (`TextModel`): there is no rich editor.

**The `.typ` is the source of truth**, and nothing about an object is kept anywhere else. `typst_objects` finds it by its tags, parses its body, gives the editor a model, and writes the body back **between the same two tags and nowhere else** (`write_object`: every byte outside kept, LF or CRLF as the file has it). The body is written in one **canonical form** — one named argument per line, two spaces of indent, a trailing comma, the arguments in the order of the command's signature (`SIGNATURES`, held equal to `lib/document.typ`'s own), a column, a row or an option on a line of its own, a short array inline — and its values are the literals of Typst's code: a string, an integer, a float in its shortest form, `true`, `false`, `none`, `auto`, a length or a ratio (`Length`), an array, a dictionary, **content** (`[…]`, kept as the markup between its brackets and never looked into: where `[#doc-value("g_k", domain: ("dead-load", "D1"))]` lives) and, for what is none of these (`width: 50% + 1cm`), the code as written (`Expr`), which an edit of the object around it keeps and which the editors refuse to edit. **What was written by hand is told apart without a hash**: a body is `canonical` where serialising what it parses to gives it back, `hand_edited` where it parses and does not (a comment, an argument out of order, a row broken over two lines, a heading written as `#heading(...)`), `unreadable` where it does not parse. Woodcore writes a canonical object back silently; a hand-edited one **only after warning** that the hand-written form will be rewritten in Woodcore's, naming what changes with the diff (`Object.diff()`, `write_object(..., force=True)`); an unreadable call is replaced by the type's defaults under the same id (`default_call`); and a heading or a paragraph that cannot be read is **never replaced** — it is shown read only and corrected in VS Code. An object removed from a file is **copied into `Sections/archives/<stamp>-<file>-<id>.typ` first**.

### The eleven commands (`lib/document.typ`)

`lib/document.typ` prints the objects, and `lib/formula.typ` imports its eleven commands **by name** — `distance`'s arrangement (§10bis); the file imports `calc-engine.typ` and `bibliography.typ` at its top and nothing from `formula.typ`, so the chain stays acyclic with no import inside a body. Each is documented, translated and exemplified like every command (§2 rule 14) and listed in the «Objets des documents» category (§10sexies). ⚠️ **The engineer's own words are content and are never looked up in the glossary** — the journal's rule (§3.3terdecies): a title, a cell, a caption, a label, a note is printed exactly as written, a string included (it is wrapped as content before it reaches `render-table`), so a use typed «Element 3» cannot match a template of the glossary and come out translated; what the engine says of its own accord — a column's default heading, the line saying what orange means, a placeholder — is `calc/i18n/strings.json`'s, in the report's language. ⚠️ **A table is set as every table of this engine is**, by `render-table` (§3.3), but for a table with no heading row, which is laid out in `lib/document.typ` itself with the same rules, insets and alignments; and **a column of a document's table is hyphenated**, which no other table is — the engineer's words in a cell are long German compounds that ran past their column, and `hyphenate: true` is set on the document's tables alone. Every refusal — a column that is not one, a cell that is none of content, a string, a number or `none`, an argument the command does not take — is a `panic` naming the command.

`doc-table` is a table of columns (`id`, `title`, `unit`, `kind`: text, number, math or wide), **hidden** columns — absent from the page and **kept in the call** —, rows keyed by column id, a caption and notes; `live-load-table` and `dead-load-table` are the same with known columns (below); `doc-field` one labelled value; `doc-checklist` a list to tick, an option with its box and, ticked, its paragraph (`only-checked` for what was chosen alone, as the accepted risks are); `doc-choice` one choice among several, the answer alone with `only-selected`, or an answer of the engineer's own; `doc-image` a file of the project with its caption, or a dashed frame saying «[Abbildung]» until the file is there; `doc-plan` an extract of a position plan (`show-plan`'s every argument, and a frame while none is chosen); `doc-signatures` the signature rows of the agreement, **a parametric block and not text**; `show-norm-list` the norms a section names, in full, each registered for the bibliography; and `doc-value` one value of the export, printed alone.

### The live loads, the dead loads, and ψ

A live-load row names a **category of SIA 261 Tabelle 8** — a drop-down in the right pane, `A1` to `H` — and its `q_k` and `Q_k` cells are `auto`, **the export's own value for that category**, read as `#val("q_k", domain: ("live-load", "B"))` reads it, so it follows the norm table and is never typed twice, or **a number**, the engineer's own, printed in the orange of a value written over with a line under the table saying what the orange means, «Reprendre» in the pane going back to the norm's. Category E has no values in the norm — SIA 261 8.2.2 leaves them to the project — so `auto` is refused naming the clause and the value is written as a number. The storey and the use are the engineer's words, written in the row by hand, and the first column, `zone`, is hidden or shown from the pane. The `load` column of a **dead-load (non-structural self-weight) table** takes a number or a value of the Variables tab. ⚠️ **A table cell never carries a footnote**, whatever level the report is compiled at: `#val` would put one in every cell at level 3 and `uniform-level` would force it, so an automatic cell and a variable put in a cell from the pane's picker are written `[#doc-value("…", domain: …)]` — `doc-value` prints the value alone, with no unit, no label and no footnote, unaffected by the level, and registers its norm for the bibliography. The pane reads such a cell back and shows the variable and not the call (`typst_objects.variable_cell`, `object_panes.variable_of`, held equal).

⚠️ **ψ0, ψ1 and ψ2 are never shown for live loads** (the engineer, 01.10.2026). The first build offered them as three optional columns and gave every instance of the live-load domain three `psi_*` variables; both are gone — no ψ column is a known column of the live-load table, a column of that id is refused, and no instance of the domain carries them. **SIA 260:2013 Anhang A, Tabelle 2 stays transcribed** in `calc/norms/sia260-2013-tab02-reduktionsbeiwerte.json` and read by `calc/norms/sia260.py` for the load combinations (§3.5), which read it where the category they scale is known: `live_load_psi` maps a category of SIA 261's Tabelle 8 to its row (A1 to A3 to A, C1 to C3 to C, every one of the twelve, category E included although it has no load), and snow is **the formula ψ = 1 − c/h0 as the norm prints it** (c = 60, 250, 1000) and is never evaluated, the norm giving no lower bound. The transcription is checked against the page — p. 33 of the German edition, and the text layers of the French and English editions, which print the same thirty-nine cells — and by planted defects (`tests/test_sia260.py`).

### Sharing a section between the documents (`calc/sharing.py`)

**The unit of sharing is the whole file**: sharing a section copies its `.typ` into the other documents' `Sections/` folders, each copy a file of its own that its document includes like any other. What stays **synchronised** is only what lies between two shared tags — `// woodcore:shared <shared-id>` … `// woodcore:/shared <shared-id>`, which may hold any Typst, objects included; **outside them each copy is free** (a document may keep only the table and drop the heading and the words around it), and a node of the tree that is a heading inside a file stands for **its whole file** (a chapter has no file and is not shared; a heading the report's entry file carries itself is no section). `share(here, mode, node_id, targets)` makes the copies, wraps the whole body after the import line in `// woodcore:shared <file-id>` where the file had no tags — **in the source too** —, writes `shared_with` on every side and records the copies as in step (calc/sync.py); `stop_sharing` takes this copy's tags off, **its content kept**, and its record with them, so that the file shows as unshared (greyed); `reconcile` writes every `shared_with` again from the tags, **the tags being the truth** and `shared_with` only what they say, written down for the tree.

A copy lies at `Sections/<id>.typ` in a CU or a BP, under **the id the section has where it comes from — the same file name is the same stable id**, which is why a shared section cannot be renamed —, at the end of the group of the same id (else of the same title, else of the document); in the report it is `Sections/<id>.typ` too, **the id as the file's stem without the report's three-digit number**, with an `#include` after the last one, and a report's file shared into a CU or a BP takes an id there made from its stem with the number taken off. The copy is the file byte for byte but for three things: its shared tags where it had none, its import line (`documents.import_line`, the one spelling valid from every folder) and a path that would no longer reach its file from the other folder, written root-absolute — **inside the block in every copy, the source included**, so that the copies start identical between their tags. Every operation reads and checks everything before it writes anything, writes each file beside itself and moves it into place (tried again on the PermissionError NextCloud's client gives on a file it has just seen written), and puts back what it had written if a later write fails; every refusal is a `SharingError` with a code (twenty) and the values it is about.

### Keeping the copies in step (`calc/sync.py`)

⚠️ **An edit only ever writes the copy of the document it was made in**, in VS Code or in Woodcore's own right pane, and **the other documents learn of it; they are not changed by it** — the engineer's rule of 01.10.2026, which **replaces the rule of the first build**, under which a shared block edited in Woodcore listed the copies that differed in an alert and then had Woodcore's version written into every copy (`plan_sync` and `apply_sync`, which did that, are gone from `calc/sharing.py`). Each document says, for each shared block and for each object inside it (compared by id), **where it stands** (`sync.STATES`, in order of severity): `in_sync`; `local` — only this copy changed since this document last synchronised; `incoming` — **orange**: another document's copy changed since, and this one did not; `conflict` — **red**: both changed and they differ; `ignored` — grey: the engineer chose «Ignorer»; `problem` — this copy's tags cannot be read, or two files of the document carry the block. «Importer les modifications» (`import_changes(here, mode, items, choices)`) takes, for what is incoming, the other document's version **between the tags only** — a whole block, or **one object alone**, rewriting that object's two tag lines —, in this document's copy alone; a conflict is asked which version to keep (`choices`: «mine», «theirs» or a document's name), each document's text being kept in the status for a diff; `ignore` and `reactivate` set and take off «Ignorer» for a file or an object, **per document and permanently, until «Réactiver»**.

**What is remembered, and where.** Each document keeps `sync.json` (format `woodcore-sync` 1.0) beside its entry file: the document's folder is what an archive of it holds and what a migration moves, so the record travels with the copies it describes — and a document template never carries it (`templates.SYNC_FILE`). It is Woodcore's own file, written whole (LF, two-space indent, fixed key order, beside itself and moved into place), never edited by hand; its contract is `sync.check_source` and there is no JSON schema for it (§14). For every shared block it holds, it records hashes — **the first sixteen hexadecimal digits of the SHA-256 of the text with its line endings made LF**, so that a file saved CRLF by one editor and LF by another holds one version — of the block's own text and of each object, **as this document last synchronised it**, and, for each other document, the hash of **this** copy (`own`) and of **that** copy (`seen`) when the two last synchronised. One base per block would not do, which is why there are two: «keep mine» in a conflict means this document has *seen* the other version and kept its own, which one hash cannot say, and a copy made by `share` inherits the source's standing with a third document while being in step with the source. A state is worked out for a part in document D against each other document O: the same text in both is in step; else `mine` is D's copy not being what D held when it last synchronised with O and `theirs` O's not being what D then saw of it — both is a conflict, `theirs` alone incoming, `mine` alone local. D's state is the worst over the others, a block's the worst over its parts, a file's over its blocks.

**Its contract is `schemas/sync.schema.json`** (v0.117, issue #33): until then the code of `sync.check_source` was the only statement of the format, against the rule that every JSON follows a schema with `schema_version`. The schema describes the format as it was written since 01.10.2026, unchanged (1.0), and `check_source` validates a record against it first -- types, the version, the format, the documents -- then checks what the schema walker cannot express (a hash's shape, an id's, the keys an entry, a relation and a pair may hold, `with` naming another document), which the schema's description lists, so the two read as one contract; `tests/test_cli_sync.py` holds the schema's constants equal to `sync.py`'s. A record that does not read names the file and the field (`sync.json.blocks.<id>.text: expected string or null, got int`), and `woodcore-cli check` stops on it. The tab's actions -- what is shared and how it stands, «Partager», «Importer les modifications», a section moved -- are also `woodcore-cli sync status|share|import|move` (build-and-release.md §12), calling the same functions.

**Settling.** Two copies found holding the same part are in step for it whatever they held before, which every read and every write records — so two copies edited the same way in VS Code never come out as a conflict later. A project **seen for the first time** starts its equal copies in step and its differing copies — with no record to say who changed — **in conflict**, for the engineer to settle. After Woodcore's own right pane has written a shared block it calls `record_local_edit`, so that a project never synchronised shows that edit as local here and incoming elsewhere and not as a conflict. Writes read everything, check everything and write every file they change at once (`changed_meanwhile` where a file moved since it was read, `write_failed` putting back what was written); every refusal is a `SyncError` with a code (twelve), and a record that cannot be read is said and never rewritten.

### Importing from another document, and moving (`calc/doc_import.py`)

«Importer depuis un autre document»: the engineer chooses the convention, the base or the report — **dynamically**, the tree under it made again with each choice — and ticks chapters, sections and, under each, the objects of its file (`importable`); `import_items(here, target_mode, source_mode, items, linked=True)` brings them in. **Whole sections arrive at the bottom of the tree** (a leaf at the end of the top level of a CU's or a BP's `structure.json`, an `#include` after the report's last one); **objects imported alone arrive in a section of their own, «Importé»** (id `imported`, its heading in the document's language), created at the bottom where there is none and written to where it already is, and drag and drop then places them. A section and some of its objects both ticked: the section wins. **What is imported stays linked** unless «copie indépendante» is ticked: a section is shared (the sharing module's rules, the same file name in both documents, so that a later edit in one turns the other orange); an object alone is **wrapped in shared tags in both files**, its shared id derived from its object id and unique in the whole project, and one standing inside a larger shared block is already linked through that block, so a linked import of it alone is refused (`inside_shared`). An independent copy carries no shared tag, a section a fresh id and an object an id free in its file. ⚠️ **An object's id is the same in every copy of its block**, the synchronisation comparing objects by id — so where the destination already holds that id (two sections of a template each have a `title` and a `p1`) the object takes a fresh one (`title-2`) in the source and in the copy, and an object that is a shared block alone cannot be renamed and is refused.

**Moving** (`move_object`): one tagged object, with its tags and, where it is a shared block alone, its shared tags, within its file or into another file of the document, above or below an object. One standing inside a **larger** shared block cannot leave it (`leaves_shared_block`) but may be reordered inside, which is an edit of that block like any other, made in this document alone — `sync.record_local_edit` is told, so that the block shows as local here and incoming elsewhere. `move_section` is `structure.move_node`, the one operation that moves a section anywhere in the tree. Every operation is all or nothing, line endings are kept, and every refusal is a `DocImportError` with a code (nineteen) beside the codes of the modules it calls.

### The preview of what is chosen (`calc/structure_preview.py`)

The centre of the tab shows **the node chosen and nothing else**: a chapter, only its printed sections (a disabled section, and everything under a disabled chapter, is left out of a chapter's page as it is left out of the document's); a section, only itself; an object, only that object; several nodes one after the other; nothing chosen, the whole document — which is the tab's own full compile and no snippet. This module works out **the Typst source of that small document**, reads the project's files and writes none. A snippet is compiled from standard input against the project's folder as the Typst root — nothing is written into the engineer's project to render a preview — so every path in it is written from the root (`include "/1_Convention d'utilisation/Sections/purpose.typ"`). It carries the least that makes a section print as it does in the document: the project's `config.typ` (`conf`) on a page **as tall as it needs to be** and with no footer or heading number; the engine; the **document** it belongs to (`wc-document`, which `show-journal` reads) and the **language** its entry file sets; for a section, the very lines the document's entry file includes it with, `set heading(offset: …)` included; for a chapter its heading; for an object **the file's preamble** — the `#import`, `#let`, `#set` and `#show` lines before its first tag, which the object may rely on — and the object's body as written, under its section's offset. A node the document does not print is **shown all the same** when it is the one chosen. A snippet says nothing of staleness and writes no stamp (calc/stamps.py); `PdfPane.request_snippet` compiles it in about half a second, one compile at a time and only the latest request. ⚠️ **It is not a live preview** — nothing tracks the cursor in VS Code, a snippet and not a Tinymist-style preview being what the engineer's rework asks for (§13).

### The content templates (`templates/documents/`, `calc/tools/build_document_templates.py`)

`templates/documents/cu/standard/` and `bp/standard/` hold, for each of the three languages, **exactly the document's own folder**: the entry `.typ`, `structure.json` and `Sections/<id>.typ`. The convention has **59 sections in 10 chapters, 48 printed by default**; the base **72 in 18, 66 printed**; **388 objects to a language** (169 and 219), 59 and 72 of them the sections' headings. **Seventeen sections are shared by default** — `scope-and-limits`, `building-description`, `transport-dimensions`, `sustainability-certification`, `ground-conditions`, `live-loads`, `superimposed-dead-loads`, `service-life`, `deformation-limits`, `settlements`, `vibrations`, `durability`, `earthquake`, `impact`, `accepted-risks`, `project-documents`, `norms` — under the **same id in both documents**, because a shared section is copied as a file and a common file name is the natural spelling, and **byte for byte between their tags** (the generator writes one file twice); whether a shared section is printed by default is decided per document (ground conditions is on in the base and off in the convention). Each document ends on its own `journal` section (`#show-journal()`), and the title page, the contact box and the table of contents are the entry file's, not sections. A section **printed by default** is the catalogue's `enabled_default`; a section switched off keeps its file.

The catalogue the generator reads is the maintainers' file and is not shipped; the generator is deterministic (a rerun on the same catalogue writes the same bytes) and `tests/test_doc_templates.py` holds what the templates must be — every one compiling in every language, ids valid, the shared sections identical, every object canonical. It is the union of the BFH's two templates (nine chapters of the convention, fifteen of the base), two office Nutzungsvereinbarungen, a Projektbasis and a Technischer Bericht, **ordered as SIA 260 orders its contents** and carrying, for each section, the clause it answers: the convention's six items are SIA 260 2.2.2's, the base's structural concept 2.5.1's and its other chapters 2.5.2's, with the BFH's fire protection, building physics and noise protection in the base. **The Technischer Bericht is not a mode**: its «Konzept Hochbau» and «Randbedingungen» went into the base's `structural-concept` and `ground`. **No client data**: no name, address, figure or date of the examples — a section that was one project's design (a school, an extra storey) is kept only as a generic optional section — the repository being shared. Swiss German throughout (never ß), French with the «maître de l'ouvrage» of SIA 260 FR and inclusive forms only with the middle dot, British English; the English terms of SIA 260 are quoted from its EN edition and the rest is the catalogue's own wording, which needs a native read (§14). A text in square brackets, `[…]`, is a prompt for the engineer to replace and never content.

What the tables of a template carry. The live-load table leaves `q_k` and `Q_k` to `auto`, so they follow the norm table. The other tables hold **example rows** — typed numbers in the call, the engineer's to overwrite — whose norm-fixed values are **written from the repository's own norm files and not from the examples**: SIA 265 Tabelle 8 and 9's timber (C24: f_m,d 14.1, f_c,0,d 12.4, f_v,d 1.5, E_0,mean 11 000, ρ_k 350; GL24h: 16.0, 16.0, 1.8, 11 500, 385 — an office Projektbasis prints 12 and 14 where Tabelle 8 gives 12.4 and 14.1), SIA 263's steels and bolts, SIA 261 Tabelle 28's unit weights; a number the library cannot supply is a placeholder `[…]`. ⚠️ **The concrete and reinforcing-steel rows leave SIA 262:2025's design values as `[…]`** — the library has no SIA 262, and the table shows only the characteristic strength and the unit weight. **Consequence classes CC1 to CC3 are kept** in `reliability-differentiation` with their source (SN EN 1990 Annex B), SIA 260 leaving the differentiation of reliability to the engineer, and **snow's ψ0 is written 1 − 60/h0 as the norm prints it**. ⚠️ **The base keeps a section `reduction-factors`** — SIA 260 Tabelle 2 as a hand-written `doc-table` — which sits oddly beside the rule that ψ is never shown for live loads, a table of the norm being no live-load table (§14). The sections the catalogue marks as shareable with the report are only marked; nothing in the report changes.

### Headings at the level they print at, objects taken out, and the whole document (v0.113)

**Headings written at the level they print at.** The engineer, 06.10.2026: «dans le document type, il doit y avoir deux égales» — a sub-section's file writes `== Projektspezifische Unterlagen` — and «le titre du chapitre doit se trouver dans un fichier .typ, éditable soit à la main soit dans Woodcore». A convention or a base whose `structure.json` says `"headings": "absolute"` (`structure.is_absolute`) is laid out so: every section file writes its headings at the level they print at, its depth in the structure; every **chapter is a file of its own**, `Sections/<chapter-id>.typ` (`structure.group_file`), holding the import line and its heading as the heading object `title` at its depth; the entry's generated block is plain `#include "Sections/<id>.typ"` lines, chapters and sections alike, in document order; and the tree reads a chapter's title off its file (`_group_title`), so `title_of`'s three languages no longer reach it. `structure.named_files` gives every file a structure names, sections and chapters, which the template checks and `save_from_document` use. An operation that moves a section to another depth — `move_node`, `share` into a document that places it elsewhere, `import` — shifts its headings with it (`shift_headings`, `fit_text`, `fit_file`), **outside its shared blocks**; `add_section` writes the new file's heading at its depth as a heading object, `add_group` writes the chapter's file, `set_title` on a chapter writes its file, and `remove_section` and `rename_section` take the chapter's file along.

⚠️ **A shared section's title stands before its shared block** (`title_out_of_shared`): the convention and the base place a shared section at different depths — the live loads at 2 in one and 3 in the other —, so a title inside the block could not be right in both. The block opens right after the title object, or after an untagged first heading line, and stays byte for byte the same in every copy; renaming the section's title is therefore an edit of this document alone and turns nothing orange elsewhere. A report's file that carries the same shared block has its title moved out too and keeps its levels, which the report's files always wrote.

⚠️ **A project made before v0.113 keeps its offsets** — its files write `=`, its chapters' titles are in its entry — and is read, previewed and compiled exactly as before (`_offset`, the legacy branches of `block_lines` and `_tree_structured`). The structure tab says so in a banner with one button, **«Écrire les titres à leur niveau réel…»**, which converts the convention and the base **together** after a question (`structure.make_absolute`, `make_absolute_folder`): each section's headings shifted by its depth less one, its title moved out of its shared block, a file written for each chapter from its title in the document's language, `"headings": "absolute"`, the entry's block written again. The printed document does not change; the test converts a project back to offsets and forward again and gets the templates byte for byte. The templates and `tests/projet-exemple` were converted by the same function (`build_document_templates.py` calls `make_absolute_folder`).

**A choice and a checklist print what is chosen** (`lib/document.typ`): `doc-choice` defaults to `only-selected: true`, the label and the answer on one line, and `doc-checklist` to `only-checked: true`, the ticked options as a list with their paragraphs — the engineer's «uniquement les choix sélectionnés doivent être affichés» for the Erdbebenzone, the Baugrundklasse and the Bauwerksklasse. `false` brings back every option with its mark; the right pane offers them all either way.

**The whole document is a row** at the top of the tree (`structure_tree.WHOLE_ID`, `st_whole_document`): a sibling of the first chapter so nothing is indented one step further for it, no box, never dragged, a drop above it being a drop above the first chapter; it is selected whenever nothing else is, and choosing it chooses nothing else, so the page is the document's.

**An object taken out stays where it stood** (`calc/removed_objects.py`, the engineer's: «aucune alerte … le user doit pouvoir réintégrer l'objet à sa position»). «Retirer» on an object asks nothing: the object is copied into `Sections/archives/<stamp>-<file>-<id>.typ` as before, cut out of its file, and recorded in `Sections/archives/removed.json` with its type, title, file and the ids of the objects before and after it (`neighbours`). The tree shows it as a `removed` row, struck through, where it stood; the pane says what it is; a right click offers **«Réintégrer à sa place»** — `restore` puts the copy back **right after the closing tag of the object that stood before it**, whatever was written between the two meanwhile, else right before the one after it, else at the end of the file, with a blank line either side, under a free id where its own was taken — and **«Retirer de la liste»**, which forgets the entry and leaves the copy. A section is still asked about, and archived whole.

### Layout templates, content templates, and the norms catalogue

A **document template** (`calc/doc_templates.py`) is what a new CU or BP is made from: a folder `<mode>/<folder>/` with a `template.json` (`schemas/document-template.schema.json`: the mode, the name and the description in three languages, the languages it exists in) and, for each language, the document's own folder. Three places, as a project template has: **builtin** (`templates/documents/`, read only: `builtin:cu/standard`, `builtin:bp/standard`), **user** (`%APPDATA%\Woodcore\templates\documents\`) and **office** (the shared folder the settings name, `shared:` being read as `office:`); a template is named `<place>:<mode>/<folder>`. `instantiate` copies the folder of the project's language into the document's folder, names the entry what the project calls it, writes its structure block from the copied `structure.json` and never overwrites. **Saving a document as a template** (`save_from_document`, «Enregistrer comme modèle…») copies the document's entry, its `structure.json` **with the enabled flags as they stand** and each section file **as the engineer wrote it** — and leaves out `Sections/archives/`, PDFs, the journal (a document's history is not its skeleton), the pictures, `sync.json` and every file no section lists; nothing is written before everything is checked, the template is staged and read back by `check`, and what an overwrite replaces, like a template `delete` takes away, is **moved into `<place>/documents/archives/` and never deleted**. Such a template usually exists in one language and is offered only for a project in that language (`list_templates(language=)`); saving the same folder again in another language adds it. **A shared section is kept as it is** — its tags and its `shared_with` —, `instantiate(siblings=…)` keeps `shared_with` only for the documents the new project has, and `settle_sharing(here)` writes every flag again from the tags once both documents are there, which is the one place a mix of templates (a user's convention with the builtin base) is brought to agree; `project_template.create` calls it.

**The layout template** («template de forme», DE «Formvorlage», EN «layout template», `calc/forms.py`, `schemas/form.schema.json`; v0.114, 06.10.2026) replaces v0.112's styles. It is the look of the three documents alone — fonts, sizes, margins, how headings and sections are set, the title page, **no data** — and lives in a folder **`Template/` at the project's Typst root** (the project's own folder for three documents): `Template/template.typ` defines `#let template(doc, lang:, region:)` and the design tokens the title page needs (the BFH form exports `sans`, `bfh-grey`, `bfh-yellow` and `muted`), `Template/form.json` states which form it is (`format: woodcore-form`, `id`, `place`, `name`, `description`), and the assets it uses — a logo — lie beside them, `image("logo-bfh.png")` resolving from there. **`config.typ`, at the root, keeps only the document's `doc-lang` and `doc-region` and the engineer's own adjustments** (`forms.config_text`): it imports `template` from `/Template/template.typ`, `conf` applies it with `show: template.with(lang:, region:)` and then, in a place the file marks, the engineer's own `set` and `show` rules, which **win over the form's** and survive the form being switched. **`title.typ`, at the root, is dedicated to the form**: the form's own title page, plain Typst the engineer edits by hand — the rows, the spacing —, importing the form's tokens from `/Template/template.typ`, replaced with the form. Three forms are builtin (`templates/forms/`, read only): **`neutral`**, the default — A4, margins of 2.5 cm, justified 11 pt text, numbered headings, the page number centred in the footer, no colour —; **`compact`** — the same with 2 cm margins and 10 pt text, so a calculation takes fewer pages —; and **`bfh`** — the Berner Fachhochschule's: its logo and grey-blue and yellow, a running header with the logo and the current chapter, the school's names in the footer, a chapter to a page, its own title page, and **all its text in Lucida Sans** (Segoe UI, then Arial, where it is not installed) — the body, the tables, the captions, the outline, the headings, the header and the footer alike, only the formulas keeping Typst's math font. A form is a folder holding `form.json`, `template.typ` and `title.typ` in one of three places, as a template has: **builtin**, **user** (`forms/` inside the engineer's folder of templates) and **shared** (`forms/` inside the office's), named `<place>:<id>`; `forms.find` also takes an id (`neutral`, `compact`) or a name in any language, and `forms.default_ref` is the settings' `forms.default`, else neutral. `forms.apply(here, form)` switches a project's form **all or nothing**: the existing `Template/` and `title.typ` — and `config.typ` where it is monolithic — are moved into `<archives>/<yymmdd-hhmmss>-forme/` and never deleted, the form's files are staged and put in place, and `config.typ` is written in the new format with the project's own `doc-lang` and `doc-region`, or left untouched where it is in it already, since it holds the engineer's adjustments; a failure puts back what was moved. A project from before keeps its one monolithic `config.typ` until a form is chosen. `import_folder`, `save_from_project` and `archive` make and take away the engineer's own forms as `doc_templates` does for contents, nothing being deleted. The styles of v0.112 are the forms `neutral` and `compact`: `templates/styles/` is gone, and `templates.replace_config`, `--style` and `create(style=)` remain only as the older names of `forms.apply`, `--form` and `form=`.

**Content templates, the report's included, and switching one** (v0.114). A **content template** («template de fond», DE «Inhaltsvorlage», EN «content template») is the sections, the objects and the text of **one** document, and `doc_templates.ALL_MODES` is now `cu`, `bp` and `rs`: the report has content templates of its own — `templates/documents/rs/standard/`, eight numbered sections (`001-einleitung` … `008-journal`) in three languages, whose language folder is the report's own folder: its entry `Statischer Rapport.typ`, `Sections/NNN-<name>.typ` in the order of the entry's `#include` lines, **no `structure.json`**, `check` holding that every include names a file there and every file there is included —, saved from a document and imported like the other two. Several can be made and imported for each document. A content template is chosen when a project is made; **switching it afterwards** (`calc/content_switch.py`, `calc/tools/content_switch_dialog.py`, «Changer de template de fond…» in the «Structure du document» tab, in each of the three documents; refused, with its reason, to a project written as one report and to one held read-only) is a **comparison and never a copy**. `compare(here, mode, template)` unites the document's sections and the template's in one tree, each node `same`, `differs`, `document_only` or `template_only` (line endings made LF, and for a CU or a BP the template's headings put at the depth the document has them at), a CU's or a BP's chapters nodes too, compared by their chapter file; under each section stand its tagged objects with a status of their own, which is information and nothing more — **nothing is chosen object by object**. Each section is given one word, `CHOICES` by status, the `DEFAULTS` keeping the document and adding what only the template has: `keep`; `take` (the template's text, the document's file archived first, or the template's section added where the document has none); `drop` (the section out of the document, its file archived); `skip` (a template's section left out). The result takes the template's order, a section only the document has being placed after the node that preceded it; for the report, sections are matched by name without their number (`001-einleitung` and `004-einleitung` are `einleitung`) and numbered again. `apply(here, mode, comparison, choices)` writes the structure.json, the section and chapter files (a file kept at another depth having its headings shifted) and the generated block — for the report the numbered files and the `#include` lines — **all or nothing**: every file read first, every one put back as it was on a failure, a file changed on disk since the comparison refusing (`changed_meanwhile`), and a CU or a BP whose headings are still written as offsets refused (`legacy_headings`: the window offers `structure.make_absolute` first). **Everything replaced or dropped goes into `<document>/Sections/archives/<yymmdd-hhmmss>-<file>`**, a chapter left with no section going with its file archived. After a write, what the documents share is brought to agree with the tags (`sharing.reconcile`), and a section taken from a template that carries a shared block another document holds is a **local edit** of this document (`sync.record_local_edit`), which the others show as incoming — never written into them. The dialog has four columns — «Section / objet», «Ce document», «Template», «Choix» —, each side said by a mark **and** a word (`=` the same, `≠` different, `●` there, `○` not there), the objects greyed under their section, «Afficher seulement les différences», a count by status, a confirmation listing what is replaced, removed and added and saying that nothing is erased, and a sentence in the window's language for every code of `content_switch.CODES` (held by a test); every question is a method, for a test to answer. **In *Paramètres*** the Templates page is **Forme | Fond**, with under «Fond» a second switch for the document, each list grouped by place — «Intégrés», «Partagés», «Mes templates» — and the chosen template shown read only; *Supprimer* archives (a builtin one is read only), *Importer un dossier…* copies one folder into «Mes templates» (`forms.import_folder`, `doc_templates.import_folder`), and the layout template *Nouveau projet* offers first is on the defaults page (`forms.default`).
