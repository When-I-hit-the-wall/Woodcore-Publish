# Calculation domains (data/calculations.json)

> How a load is a domain whose instances are Excel sheets; tables, results, groups, headings.
>
> Moved verbatim from CLAUDE.md (§3.3) on 2026-10-07. The § numbers are kept as stable anchors: `docs/README.md` maps every § to its file.

### 3.3 Calculation domains — `data/calculations.json`

A load is not a row in a registry: it is a **domain** with **instances**.

- A **domain** is one kind of calculation — `snow-load`, `dead-load`, `wind-load`, `live-load`. It declares an Excel **sheet prefix**, which side produces its numbers (`engine`: `excel`, `python`, or `norm` for a domain read from a norm table, §3.3septies — a norm domain has no sheet prefix and its instances name no workbook and no sheet, which is checked both ways) and, since v0.28, which kind of **`action`** it is in SIA 260's terms — `permanent` (G: `dead-load`) or `variable` (Q: `snow-load`, `wind-load`) — and not a workbook, since its sheets may sit in several. `action` is a constant of the domain module (`ACTION`, beside `ENGINE`), exported on the domain and validated against those two values: it is what Woodcore groups the loads by (§10quater), and what a load combination will pick its factors by (§3.5), so it lives where the load is calculated rather than in either of them.
- An **instance** is one sheet carrying that prefix, in any of the project's load workbooks: `SL-Dach1`, `SL`, `EL+AL-Fassade`, `WL-Velo`, ... One sheet, one case of the calculation. For a domain read from a norm table, it is one row of that table instead — a category of Nutzfläche, `A1` … `H` (§3.3septies) — addressed exactly the same way.

That is the whole mechanism, and it exists because the workbook itself says so: its `Objekt` sheet instructs the engineer that *"Blätter können kopiert werden"* and that *"Bauteilname wird von Blattname übernommen"*. So **copying a sheet in Excel adds that case to the export** — no Python edit, no id to invent. `calc/registry.py` discovers the sheets. ⚠️ **`Sections/004-einwirkungen.typ` names the cases it prints**, each at the level the report wants it — the engineer's choice (v0.79, periodic audit 260916, B4), where v0.18 wrote an `ids(domain)` loop — so a copied sheet reaches the page when it is named there, or through that loop; `EL+AL-Wand` is exported and not printed today.

**The load workbooks are found the same way, by name (v0.26).** Every file directly in the project folder whose name contains `Belastungsannahmen` and ends in `.xlsm` or `.xlsx` is a load workbook — `Belastungsannahmen.xlsm`, an office's numbered `02_Belastungsannahmen.xlsm`, a second file for an annex — and every one of them is read; `registry.py` states the pattern (`WORKBOOK_NAME`, `WORKBOOK_SUFFIXES`), `io_excel.find_workbooks()` applies it. Both tests ignore case, as Windows does. Excel's `~$` lock files are skipped (they match the pattern while the workbook is open, which is when the engineer builds), subfolders are not searched (an archived copy must not become a second set of loads), and the files are taken in file-name order, which is therefore the order their cases come out in: all of `02_...`'s sheets, then all of `Belastungsannahmen.xlsm`'s, each in tab order. Which files were picked up is printed on every export. ⚠️ **Finding none stops the export only where the last one read a workbook that is gone** (v0.89.1, the engineer's rule; `registry.open_workbooks`): `data/project.json` names every workbook an export read, and where it names a load workbook and the folder holds none, the export stops naming it — renamed out of the pattern, moved into a subfolder or not synced yet, it would otherwise look exactly like a project without loads, and the export would write the report's loads away. A project no export has read one for — a new project — is exported **without loads** — with a warning until v0.116, and since v0.117 with one line of information on stdout (`export_all: no load workbook in … -- loads: none`), which the window does not show as a warning (the engineer: «cette erreur ne doit plus être affichée»; the loads will one day be computed by Woodcore itself, §13): the three sheet domains carry no case, the live loads of SIA 261 Tabelle 8 are all there, and positions, plans and connectors go through. A project that deliberately gave up its loads is exported without them once its `data/project.json` is deleted, which the stop names. Until v0.89.1 finding none was a blocking error whatever the project.

Every instance is the same `{vars, steps, checks}` record §3.1 defines, plus three fields of its own:

- **An instance entered in Woodcore (schema 1.5, issues #35-#37, D-04)** is computed in Python from a source of the project, `Woodcore-Datei/loads/{dead,snow,wind}/<id>.json`, by the module `registry.SOURCE_MODULES` names for its domain (`dead_load_source`, `snow_source`, `wind_source`), and joins the sheets' instances under the same domain, after them, in file-name order. It carries **`engine: "python"`** -- its own, where the domain's was `excel` (the snow's and the wind's are `python` too since v0.120, a sheet's inputs being computed by the same code, docs/domain/loads.md §3.3bis) -- and **`source_file`** (`loads/snow/SN-01.json`), and no `workbook` nor `sheet`; `validation.validate_calculations_business` holds the three together, and an instance of another engine than its domain's with no `source_file` is refused. **An id a sheet and a source both carry is refused**, naming the source and the workbook. A domain whose cases are all sources is not warned about for having no sheet. It may carry **`figures`** -- `[{file, title, level, width}]`, the SVG under `data/calculations/` (in a project laid out by folders, since v0.119, `Permanent-loads/Exports/Figures/`, named in the JSON from the Typst root -- issue #64, docs/architecture/layout.md §11) (`registry.write_files`, which removes the drawings no case carries any more) --, printed by `show-calc` above its tables from their own level. `schema_version` is 1.5; an export at 1.4 is still read. `registry.export(here)` rebuilds `calculations.json` alone -- what a tab of loads runs when a case is saved.
- **`workbook`** and **`sheet`**: the file and the sheet it was read from. On the instance, not the domain, since one domain's sheets may come from several workbooks; every var's `source` names them too (`excel:02_Belastungsannahmen.xlsm!SL!H17`). Both are absent from an instance of a norm domain, which has no file and no sheet behind it — a required field there would be an empty string pretending to be one (§3.3septies).
- **`results`**: the names of the vars that are the calculation's final results — what `show-calc` prints at level 1. A *list*, because one sheet may legitimately produce several: `SL-Dach2`'s load model yields both q_(k,11) and q_(k,12), and neither is "the" answer.
- **`tables`** (optional): tabular evidence, as a *list* — one calculation may need several (v0.29) — each in either of two shapes: the *working* behind a value (the layer build-up behind a permanent load, §3.3ter; the local wind forces, §3.3quater) or the *answer* itself, where a calculation ends on a set of cases rather than on one number (the global wind forces, §3.3quater). Which of the two each one is, is stated rather than guessed: **`level`** says from which report level it is printed (3 when absent — the working is for a checker), and **`place`** whether it sits `above` the values it explains (the default) or `below` the values leading to it; tables on the same side keep the order of the list. Values stay numbers; Typst formats them. A table whose cells are numbers rather than vars may say where those numbers come from in a **`source`**, in a var's format (`python:domains/wind.py`) — the one record that a table was computed in Python on a domain whose `engine` is `excel`. Until schema 1.3 the key was a single `table`; an instance still carrying one is refused, since the display layer reads only the list and would drop it without a word.

  Each column states what it holds and never how wide it is — **one exception since v0.117: the list of the positions** (`position-list-table`, the only table whose columns carry an optional `width`, a length or a percentage of the text width, and which sets `fit: true`; a table read from the data carries neither, and `render-table` lays it out as before; docs/decisions.md): such a table is given every column's width from what its cells hold, its sum never more than the text area, its rows kept whole across pages with the heading repeated, its text hyphenated in the report's language; and the widths that were asked for are reduced, with a note, only where they leave the others less than 2 em: `{"label": "Dicke", "kind": "number", "unit": "m"}`, `kind` being `math` (the cell is Typst math source, evaluated like a `symbol`), `value` (the cell *names a var* of the same instance and the table prints that var's value — so the number lives in one place only, the var is not set out on a row of its own as well, and it comes out bold where it is one of the instance's `results`; since v0.31 a `value` column may also hold plain numbers in its rows, where only its `totals` row names a var — a connection's Δx² column, summed into I_p,x), `wide` (the one column that takes the leftover width), `text` or `number`. A column's `unit` is a field of its own, never typed into the label: the header sets it on a second line (`Dicke` over `[m]`), which is what lets a column of two-decimal numbers be as narrow as its own name, and the brackets are display, like every other unit's. A column headed by a *symbol* rather than by a word carries it as Typst math source in **`label_math`** (`q_k` and `Q_k` over the two value columns of Tabelle 8, §3.3septies), its `label` staying that name in plain text, for Woodcore and anything else reading the data as text. A column may also carry a **`group`**, which names a heading spanning it and the consecutive columns sharing it (`Bezugsfläche` over `b·h`, `d·h`, `d·b`), set on a header line of its own — a var's `group` idea, applied to columns.

  A `tables` entry may carry **no grid at all** and be only its title, its note and its **`figures`** (v0.84): SIA 265's Figur 45, one plate per thickness, whose corners are written out as the formulas of Tabellen 45/46 above it rather than tabulated (§3.3nonies). It goes through `render-table` like every other table so that a plate of figures carries its own `level` and its own `place` rather than needing a mechanism of its own; its `columns` and `rows` are empty lists.

  A `group` over a **single** column names that column rather than spanning a run of them — a connector's «$d$ = 10 mm» over Tabelle 24's distances, every one of which is a multiple of it (v0.84, the engineer: the cell that was empty). It is set at its own column's alignment rather than centred, its label may carry math between dollars, and it takes no rule under it: there is nothing for a rule to say about how far a name over one column reaches.

  A table may mark rows of its own with **`highlight`**, a list of body-row indices counted from 0: those rows are set bold on a tinted ground. It is how a norm table shows the one row this calculation reads — its category in Tabelle 8 (§3.3septies) — so that the value quoted beside the table can be found in it at a glance. Which rows those are is the data's to say; the colour is one constant in `lib/calc-engine.typ` (`table-highlight`). An index the table does not have stops the export.

  Optional `totals` rows have the shape of a `rows` entry and are set bold under a rule — the sums the rows above add up to; since v0.84 that is the same thin rule which closes the headings, both parting one kind of row from another, where it was a heavier one while the table was a grid and had to be seen among its lines; an optional `note` carries the prose under the table; and an optional **`formula`** (with the `norm`/`norm_ref` cited beside it) is the formula the table evaluates, set in letters above it: for a calculation whose answer is a table, that formula is the letters line and the table is its numbers. Since v0.37 `render-table` also takes a list of formulas, one row each, and sets them without a citation when the table has no `norm` — a table built inside `show-polar-moment`, whose reference is cited once beside its heading. ⚠️ **The head of such a table — its title and its formulas — is set to its ink** (v0.97, `top-edge`/`bottom-edge: "bounds"`): a built-up formula, a fraction or a root, reaches well above and below the line box its text edges give it, and that box is what its row and every gap around it are measured against, so at 11pt the ink of the polar moment's superposition stood 5 pt outside its row either side — the 1 em between two formulas left 1 pt of white, and the 0.4 em under the last left 3 pt before the table's own thick rule, which the superscript on a tall bracket then all but touched (the engineer: «il n'y a pas assez d'espace dans le moment polaire entre F_i^* et le tableau»). Measured to the ink, every gap in the head is the white it says it is: 0.45 em under the title, 1 em between two formulas, 0.5 em above the table. It replaces the push v0.32 put on the *first* formula alone — the one side a push can reach, and measured against the line box rather than the ink — and it moves the two kinds of table that carry a formula: the polar moment's superposition and the wind load's two, whose product was 1 pt above its own rule.

  **A table is three rules and nothing else** (v0.84). A thick one (`rule-thick`, 1 pt) above the headings and under the last row, closing the table, and a thin one (`rule-thin`, 0.5 pt) under the headings, under a group's name and above the `totals`, parting one kind of row from another. **No vertical rule, no box around a cell, no grid** — every cell was drawn in a 0.4 pt grey grid until v0.84. What tells one column from the next is the space between them (5 pt either side, where it was 4) and **what each one holds**: a `number` or a `value` column is read from the **right**, so the digits line up down the column; a `math` column is **centred**, being a column of symbols (`g_k`/`a_k` over a layer build-up) — and where it holds numbers instead, as SIA 261's Tabelle 8 does, its footnote markers hang off the right and would defeat a right alignment anyway; `text` and `wide` read from the **left**, like the prose around them (`column-align`). A header follows its own column, so a numeric heading stands over its last digit. **A cell is set ragged, never justified** (`par(justify: false)` in every table, v0.87): a wide cell justified to its column spread its words across it — `find`'s text values and the Beispiel column of SIA 261's Tabelle 8, which rewraps. ⚠️ **The rule under a group's name spans exactly the columns that name covers** (`group-spans`, `group-rules`) — «in Faserrichtung» over Tabelle 24's two, «Bezugsfläche» over the wind's three — and it is what now says how far a group reaches, a vertical rule no longer being there to say it. ⚠️ **Both of the header's rules are placed inside `table.header`**, so a table that breaks carries them onto the next page with its headings; an hline written outside it is not repeated, and the continued page would show headings with nothing above or below them.

  **Every table is centred in the space it has** (v0.32): `render-table` measures it, and one narrower than the calculation's column — the text width less the citation column and its gutter — is centred in that column, its title and note following its width; one that is wider, or has a `wide` column, takes the full text width as before (the layer build-ups, the local wind forces).

  **A table's title is a numbered caption above it** (v0.114, the engineer: «le titre doit être numéroté … centré par rapport au tableau, pas en italique … comme le numéro des images, sauf au-dessus»): `render-table` wraps a titled table in a real `figure(kind: table)` (`table-figure`), so it reads «Tabelle 1: Schichtaufbau» — the counter, the supplement in the document's language, the separator and the `show figure.caption` of the project's `config.typ` being the ones a picture's «Abbildung 1: …» takes — set **above** the table, upright, centred in the column the table is centred in and so over the table, wrapping to that column rather than to a narrow table's own width. A table whose formula is printed above it (§3.3quater, §3.3quinquies) has its caption above the formula. A title of `none`, `[]` or `""` is no figure and takes no number (a document's key-value list without a caption, `show-norm-list`). ⚠️ **A plate of figures with no grid** — a connector's Figur 45 under its k_β (§3.3nonies) — is a `figure(kind: image)`, numbered «Abbildung» with its caption **under** it, as every picture's is. `#distance`'s tables take their title as their caption too, their citation on a line of its own above it in the right-hand column. The figure is made breakable inside `table-figure`, so a long table still breaks with its header repeated, and the «kept whole if shorter than a page» rule below is unchanged. Accepted price: a list of the tables (`outline(target: figure.where(kind: table))`, which the BFH template prints) now lists every calculation table, dozens in a report.

  **A table is set at the text's own size** (v0.32). Its cells, headers and title were 8 pt and 9 pt; they now inherit the document's 11 pt, and only the note under it stays small, like the citations. It keeps **`table-spacing` (1.6 em)** clear of the text before and after it. Before v0.32 that gap was 0.6 em and 0.8 em, less than the 1 em between two lines of a calculation. The one exception is a table opening a calculation right under its heading, which keeps to that heading's 0.7 em (`above:`).

  **A table shorter than a page is kept whole** with its title and formula: where the rest of a page cannot take it, it moves to the next page rather than leave its heading behind. Only a longer one breaks, its header rows repeated on the next page. The test is the table's measured height against the page's text height, which `layout()` reports wherever on the page the table falls (§13).

Notes:
- `choices` are read from the workbook's own `Dropdowns` sheet, never restated in Python — a report footnote cannot then disagree with the list the engineer sees in Excel.
- A var may carry a **`group`**, which is presentation and nothing else: consecutive input vars sharing a group are printed on one row, joined by a semicolon (`ce`/`ct` as `beiwerte`, `L`/`B` as `geometrie`, `alpha_1`/`alpha_2`, `mu_11`/`mu_12`), instead of taking a row each. Only *consecutive* ones, so a step between them still breaks the run, and the row keeps the first var's norm reference — a group whose members cited different clauses would be a grouping mistake in the data. The var that *opens* a run may also carry a **`group_label`**, printed before it (`Gebäude Geometrie: L = 20.18 m; B = 7.8 m`); a group without one is printed bare, as `ce`/`ct` are. Both sit on the var, next to `level`, because which values the report shows side by side, and what to call them, is decided where the calculation is, not in `Sections/*.typ`. ⚠️ Since v0.84 a var that **joins a run already open** and carries a `group_label` names itself *inside* that row — `Bauteil 1: ρ_(k,1) = 350 kg/m³; t_1 = 50 mm; Bauteil 2: ρ_(k,2) = …` — so one line carries the material of a connection's two members where two groups one under the other took a line each to say the same thing.
- A var may also carry **`keep`** (v0.84): it states an *input of the calculation* and keeps its own row even where an intermediate step's substituted formula already shows its number. The default is the rule `show-calc` has always applied — an operand of an intermediate step is not set out twice — and it is right for a value that exists only to be fed into the next line and wrong for the ones a reader looks up first. A dowel connection is what made the difference visible: its diameter, each member's density and each member's thickness became the operand of a formula of its own the moment SIA 265's own tables were written out as formulas (§3.3nonies), and every one of them would have vanished from the page.
- A var may carry a **`heading`** (v0.84): a line of its own **above** it, naming the run of calculations it opens — «Charakteristische Lochleibungsfestigkeiten für C24», which the report sets with its own colon so a French one keeps its narrow space. It is the way the Bemessungsbeispiele zur SIA 265 set a block (p. 291) and the engineer asked for it in those words; like `group` and `inline` it belongs to the calculation, since which runs a reader groups is something the calculation knows and the display cannot. ⚠️ It is printed **where that var's own first row is printed**, so it follows every rule that decides whether that row exists at all: a var this level hides announces nothing, and neither does one absorbed into an intermediate step's substituted formula, nor one that merely joins a group's row already open. A heading therefore goes on a var that is certainly printed — the first of the run, `keep` where it is an operand — and `tests/test_connectors.py` holds that no heading of a dowel record is ever dropped, a trap that caught three of them while v0.84 was written.
- A `step` may carry a **`description`** as well as a `formula`: it explains the working (what the formula's symbols stand for, which rows of a source table it sums) and is shown as a footnote on the formula. It belongs on the step rather than on the result var because a result var is never printed with notes — it is a result, not an input.
- A `step` may also declare itself **`bold`**: its numbers line is an *answer* even though its result is not one of the instance's `results` — the wind load's Staudruck q_p, which its own sheet sets apart from the six forces built on it. It is read exactly like `results` membership, and in both places that reads it: the line is set bold, and the step's operands keep their own rows instead of being absorbed into its substituted formula (§10bis). Presentation, like a var's `group`, and stated here for the same reason — which value a calculation puts its weight on is a property of the calculation.
- A `step` may declare itself **`inline`** (v0.84): its formula in letters, the same formula in numbers and the answer are set on **one** row — `M_(u,k) = 0.3 · f_(u,k) · d^2.6 = 0.3 · 510 · 10^2.6 = 60910.397 Nmm` — instead of the two the display gives by default (§10bis). It is a property of the *formula* and not of the report: whether a formula is short enough to be read across one line is something the calculation knows and the display cannot. A **bounded** formula is never set inline, having no numbers line to join, and where the substitution would say nothing new — no operand appears in the formula, or the substitution *is* the answer, as `k_(β,1,2) = k_(β,max)` is — the numbers are left out rather than printed twice.
- Two domains must not claim the same sheet: a prefix collision is a blocking export error, since one sheet is one calculation.
- ⚠️ *Retired by the spec 2026-10-21-commandes-typst-refonte (lot 19): `show-calc` -- write #include domain-file(kind, id) -- a load ("snow-load", "wind-load", "dead-load", "live-load"), a connector, a polar moment ("connection"), a script: its file, written out by the export, printed where the section includes it. What follows describes it as it was.* Two workbooks must not both hold a sheet of the same name: the sheet name *is* the instance id the report addresses (`show-calc("snow-load", "SL-Dach1")`), so it has to be unique across every load workbook at once. That is a blocking export error naming both files — renaming one sheet is the fix — rather than one of the two silently winning.
- A sheet is read against **its own workbook's** lookup tables — the dead load's material library, the `Dropdowns` sheet — never another's, and a workbook without a single sheet of a domain is not asked for that domain's tables at all.
- A domain that finds no sheet in any workbook is a **warning**, not an error — a project may genuinely have no facade, or no snow.
