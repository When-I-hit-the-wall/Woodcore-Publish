## 10quater. Woodcore's window (calc/tools/woodcore_gui.py)

**Adding a tab: one structure for every tab (19.10.2026, spec 2026-10-19-base-saine-nettoyage, ARCH-001, solution B).** A tab is declared once, a `TabSpec` in `calc/tools/tab_registry.py` -- its key, its class, its group and sub-title in the side navigation, the documents that show it, whether it holds one document's own work --, and everything the window reads is derived from that list (`TABS`, `NAV_GROUPS`, `NAV_SECTIONS`, `MODE_TABS`, `MODE_BOUND`). Its class is one of four kinds, each the same for every tab of the kind (`tests/test_tab_registry.py`):

* **an editor of sources** derives from `source_editor.SourceEditorTab`, which carries the list in folders with its archive, the draft's actions (*Nouveau*, *Dupliquer*, *Supprimer*, back to what is saved), Ctrl+S, the question about unsaved changes and the export -- **the four canvases' list too since v0.120** (issue #69, UI-001: «Schémas», «Statique», the plans and the fire plans, «Moment polaire» say what differs through its hooks `listed`, `draft_text`, `draft_group`, `take_group`, `list_selection`, `show_empty_hint`, `on_row_again`, `after_row_loaded`, `export_listed`; a drop into a folder saves the draft first where it can, asks only where it cannot, and says a file the disk refuses in the status bar, `list_write_failed`, last); the tab says where its sources lie (`sources_dir`), the prefix of its words (`WORDS`), how a source is made and exported (`make_source`, `export_sources`), and builds its form and its result;
* **an editor of a drawing** derives from `canvas_editor.CanvasEditorTab` -- the same, and «Annuler»/«Rétablir» (`push_history`, `snapshot`, `replace_source`); its canvas derives from `canvas_base.CanvasBase` (zoom, grid, cursor, snap marker, handles, tracking -- its own values as class attributes: `MODEL`, `TOOLS`, `ROUND`, `MIN_ZOOM`, `MAX_ZOOM`, `GRID_STEPS`, `GRID_MIN_PX`, `SELECT_COLOUR`), draws its figure with `canvas_items.SvgLayer` and its icons with `svg_icons.svg_icon`, and its engine names its colours from lib/figure-palette.json (`svg_draw.colour`);
* **a tab with «Affichage»** mixes in `display_view.DisplayTab`: one `set_view`, compiling nothing before the tab is first shown (`live`), `prepare_display` saying what the display is told before it opens;
* **a tab to come** is a `reserved_tab.ReservedTab`.

Its writers are refused in a project opened read-only, wherever they are defined -- its class, a mixin, a base it shares -- and followed by the domains' files where its class says `SYNC_DOMAIN` (`calc/tools/tab_guard.py`). Its icon goes in `chrome.ICONS`, its title in the window's words in three languages.

**Its name (v0.96).** The window was «the Katalog», and «the Typst-Katalog» before v0.83, until the engineer asked for a word common to French, German and English; it is **Woodcore** — the program's own name — and «Woodcore's window» where the window is set against the command line or the export. Its module is `calc/tools/woodcore_gui.py` and its class `MainWindow`; `calc/tools/catalog_gui.py`, the shim that ran it under its old name for the launchers installed with 0.83 to 0.90, was removed in v0.120 (spec 2026-10-19-base-saine-nettoyage, REQ-001): a launcher that old is updated by installing this version. Every text the window writes says Woodcore — the message boxes' titles, the stall log's header — and `tests/test_i18n.py` refuses «Katalog» in any `STRINGS`, message-box title or launcher message.

The reference workbook answers "which arguments exist"; writing a section also wants the answer to "what is this value, where does it come from, and what do I paste to print it" — without leaving the editor for a spreadsheet. **`Woodcore.bat`**, beside the code, opens a small window that does exactly that, on one project (`python calc/tools/woodcore_gui.py --project <file>.woodcore` does the same from a terminal): the one named as its argument — a `.woodcore` dropped on the `.bat`, or double-clicked once Woodcore is installed —, else `WOODCORE_PROJECT`'s; started without one it opens on the start page (v0.83, below). The window's title names its project, «Musterprojekt — Woodcore», with «•» before it while a tab holds unsaved changes (v0.82, v0.83). Installed, the same window is `Woodcore.exe` (§12). A PySide6 (Qt) window since v0.30 — tkinter before it (§13) — carrying its own icon in its title bar and on its taskbar button.

**The start page, the *Fichier* menu and the lock (v0.83).** Started without a project, Woodcore opens on its start page (`calc/tools/home_page.py`), the way Word opens on its own: the projects opened lately, the last first and a dozen at most (`recent_projects` in the user's settings, `usersettings.remember`), each with its number, its folder, when it was last exported (the time of `data/calculations.json` since v0.122, `project.last_export`: the «Projet» tab rewrites `data/project.json` as a title page is saved) and the version of the engine its export was written with (`_woodcore/VERSION`); where the list is empty, the project beside the code's checkout is offered. A project no longer where it was — moved, renamed, or not synced by NextCloud on this machine yet — is greyed, and choosing it offers to take it off the list rather than failing. Below the list, *Ouvrir…*, *Nouveau projet…* and *Convertir un ancien dossier…*; a `.woodcore` dropped anywhere on the page opens it, and Enter opens the one selected, the last one opened. *Nouveau projet* asks where and what the title page says — the project's name, number, client, address, office, author and checker — and creates the folder from `templates/projet/` (§12, `calc/project_template.py`); *Convertir un ancien dossier* writes a `.woodcore` into a folder laid out before Woodcore, naming its parts where they stand, and moves nothing (§12). ⚠️ **One project per process, as v0.81 decided.** The page opens a project in its own process, which has none yet, and hands over to the window; from the window the *Fichier* menu — *Nouveau projet*, *Ouvrir* (Ctrl+O), *Projets récents*, *Ouvrir dans une nouvelle fenêtre*, *Fermer le projet*, *Propriétés du projet*, *Ouvrir le dossier du projet*, *Ouvrir le PDF*, *Ouvrir dans VS Code*, *Quitter* — opens another project in a new process (`relaunch`), and *Ouvrir* and *Fermer le projet* close this window first, through `closeEvent`, which asks for what is unsaved as closing always does: an engineer who chooses to stay keeps the window and no second process starts. None of it runs while an export or a compilation does. *Nouveau projet* and *Ouvrir dans une nouvelle fenêtre* leave the window open, as Word leaves a document. *Propriétés du projet* rewrites the `.woodcore`'s details and the Woodcore version the project asks to be opened with (`woodcore_version`, the launcher's, §12) through `project.update`, which keeps every key it is not given; the title page takes them at the next export. *Ouvrir dans VS Code* starts `Code.exe` itself on the project's folder and its report — `code` on the PATH is a `.cmd`, which cannot be started without a console window. From the sources only, *Ouvrir les fichiers .woodcore avec ces sources* tells the installed launcher to start this checkout rather than an installed version (`launcher.dev_checkout` in the settings). ⚠️ **The lock.** A window opening a project writes `<name>.woodcore.lock` beside its `.woodcore` — the user, the machine, the process and since when (`calc/project_lock.py`) — and removes it when it closes, or when its process ends. A second window finding one held by someone else asks: *Lecture seule*, *Ouvrir quand même* (the lock taken over) or *Annuler*. A lock this machine left for a process that no longer runs is stale and taken over without asking; one another machine left is shown with its time, for the engineer to judge. ⚠️ Not `~$Musterprojekt.woodcore`, as the plan had it and as Word names its own: NextCloud's default exclusion list carries `~$*`, so such a file is never synced and the other machine would never see it. A lock reaches the other machine when NextCloud has synced it, a few seconds later: it is advice, not a guarantee, and the command line does not look at it. **Read-only** means a red banner naming who holds the project, «(lecture seule)» in the title, *Importer Excel*, *Exporter PDF* and *Propriétés du projet* refused, the empty folders kept for the session only, and every way an editor tab writes a source refused and said so — its *Enregistrer* and Ctrl+S, *Supprimer*, a drop into a folder or into «Archives» or out of it, and the plans *Nouveau* makes from several pages of a PDF: `WRITERS`, wrapped once on the five tab classes and on `source_archive.Actions` rather than in each of them (§13). The forms themselves stay editable, to look and to try. **Since v0.122 (issue #90) *Nouveau projet* asks the project's name, its place and its language, and nothing else** (`home_page.ProjectDialog`): the project is made without any document (`project_template.create_skeleton`), the window opens on its report, on the «Projet» tab, where the title page, the form and each document's content template are chosen, each document made when it is wanted (`docs/ui/tab-project.md`); *Propriétés du projet* opens that tab, its dialog gone.

**What it showed, until v0.117.** The *Charges / Lasten / Loads* tab listed every load domain of `data/calculations.json` as a tree — action, domain, case, var — with each var's symbol, value, unit, label, level, norm and source (the cell in Excel's notation, *Python · <module>*, or the norm table), results starred, «Résultats seulement» on by default, the details of a row — workbook, sheet, cell, the formula of its step, its `choices`, a case's `tables` as aligned text — *Ouvrir le classeur*, and, since v0.117, its calls in *Affichage*. ⚠️ **It was retired in v0.117** (the engineer's issue 13: «Supprimer l'onglet *Charges* une fois vérifié qu'aucune de ses variables ne manque dans *Variables*»; spec `2026-10-08-onglet-variables-trois-colonnes`): every value it listed is the Variables tab's (below), with its level, norm, source, formula, choices and workbook, and so are its calls — `val`, `var`, `show-input`, `var-of`, `value-of` for a value; `show-calc`, `show-live-load`, each `show-check`, the loop over the cases and the two summary tables for a case — and `tests/test_variable_sources.py` (`test_no_variable_of_the_loads_tab_is_missing`) holds that none of its variables is missing. Not carried over, by the engineer's choice: a case's `tables` as text (the report prints them, `show-calc`), the copy by double-click, Ctrl+C and right-click (D-008: one copies from *Affichage*), and «Résultats seulement» on by default (a box, off, D-007).

Every call the window offers needs the import line, `#import "../commands.typ": *`, the one every section starts with (§10bis). A binding's identifier is the var name with `_` → `-` (`s_k` → `s-k`), and a name that would shadow a Typst global gets `-var` appended — `#let h = ...` would otherwise silently replace `h()` for the rest of the file.

**Where the loads come from, and what the window may change.** The window reads the export and nothing else: `data/calculations.json` is the validated file Typst reads, so every call it copies compiles (verified in v0.28 by compiling all 801 of them). A banner warns when a load workbook was saved after that export (since v0.33 also `Positionen.xlsx`, where the positions come from, against `data/positions-index.json`). **Importer Excel** reruns `calc/export_all.py` in its own process, exactly as `woodcore-cli export` does -- with `--project` naming the window's own project since v0.81, the window having been started on one (`woodcore_gui.py --project <file>`, else the one `project.current()` finds) — a failed export shows the exporter's own message (the one naming the cell) and leaves the previous data on screen, export_all never writing half an export. Where the project's copy of the engine was written by an older version, by none a `VERSION` names (*unknown*, since v0.87) or edited by hand, the window asks before the export replaces it — «Mettre à jour et exporter» («Écraser et exporter» for an edited copy) or «Annuler», with «Voir les différences…» beside them (`engine_consent`, v0.82, §12); a copy a newer program wrote is refused, the box naming the version that wrote it. Since v0.87 the same question is put as the project opens, in the same box (below). It was *Réexporter depuis Excel* until v0.62; the operation did not change, only the name it is asked for by. **Exporter PDF**, beside it since v0.62, does that and then compiles: `typst compile` on the project's `Statischer Rapport.typ`, writing `Statischer Rapport.pdf` beside it, in the report's own folder since v0.87 (beside the workbooks until then) — the project's `report` and `pdf`, the deliverable every build route names (§12) — with `typst` found as `woodcore-cli` finds it (`project.typst_executable`). Its order is the command line's too, and so is the rule behind the order: the compilation runs only if the export exited 0, so a defect in a sheet stops the chain where the export stops it and the PDF that was there stays as it was. A compilation that succeeds opens the PDF. Those two are the window's only actions on the loads. *Ouvrir le classeur*, the Variables tab's since v0.117, opens the workbook a variable or a case was read from. (Its other action on the project, since v0.31, is saving a connection — below.)

**The engine is checked when a project opens** (v0.87, second half, the engineer: «Est-il possible que, lors de l'ouverture d'un projet qui tourne sur un ancien moteur, un message demande si le user veut uploader le moteur à la dernière version ?»). `check_engine` is queued by `open_project` once the window is on screen, before `check_dependencies` — the project just opened before the machine's packages — and is skipped under `--self-test`, where nobody is there to answer. It makes the comparison an export makes (`project.engine_state`, §12), and each state gets what an export would do with it: the program's own or a *current* copy, nothing; an *absent* one, or a *stale* one — another build of this same version, the sources edited since — copied without a word, the status bar saying «Moteur Typst du projet mis à jour vers Woodcore 0.87.0.»; an *older*, *unknown* or *edited* one, a question — «Ce projet utilise le moteur de Woodcore 0.83.0. Le mettre à jour vers 0.87.0 ? Le rapport peut s'imprimer différemment ensuite.» — answered by «Mettre à jour» («Écraser» for an edited copy), «Voir les différences…», which shows the project's copy against the program's as a unified diff in a window of its own and then asks again, or «Plus tard», which writes nothing and asks again at the next opening; a *newer* one is not asked about at all: `open_project` opens such a project **read-only** (v0.87, the engineer's yes), its lock let go and its red banner naming the version that wrote it (`read_only_newer_banner`) — this program would refuse to export into it, and a drawing saved from one of its tabs would still have re-exported its part of `data/` with older code. The launcher, which starts the version a double-clicked project asks for, says «Installez Woodcore {version} ou une version plus récente pour ouvrir ce projet» where none installed is recent enough. A project opened read-only is asked nothing and written nothing. ⚠️ **One box for the two places**: `engine_box` and `ask_engine` build and ask the question at the opening and at an export alike, the export keeping its own two buttons, so the two cannot come to say different things; and «Voir les différences…» is offered for an older and an unknown copy too, where until then the difference was Qt's own «Afficher les détails», for an edited copy alone. A copy that cannot be written — a file held open, a folder not synced yet — is said in a box rather than lost.

⚠️ **«Importer Excel» is «Import données» since v0.98** (§3.3duodecies): the one action reads the load workbooks, `Positionen.xlsx` and every source Woodcore drew -- **and** every RFEM export the project named, until the RFEM import was retired in 0.117 --, so a word that says «Excel» says less than the button does — *Daten importieren*, *Import data*. Its menu's one entry names what that takes in rather than repeating the button's word alone. ⚠️ Renaming it is not only three strings: the messages that tell the engineer to click it name it too, and `tests/test_pdf_button.py` holds every word the button has ever carried as forbidden in them — which is what caught the German `»Aus Excel importieren«` and the English `“Import from Excel”` when the first pass searched only for the French `«…»`.

**Both are split buttons** (v0.62): the button itself acts, and the little arrow beside it opens a menu. *Importer Excel*'s holds one entry, its own — there is one way to import, the export `woodcore-cli export` runs first, and the arrow says so rather than suggesting there are others. *Exporter PDF*'s holds the three things `woodcore-cli export` takes: *Tel qu'écrit (document)*, a *Niveau de détail de base* 1/2/3 (`--level`, the base the per-call overrides apply on top of), a *Niveau de détail uniforme* 1/2/3 (`--uniform`, those overrides ignored; issue #20 named both so, their entries staying «Niveau 1/2/3») and a language, *Langue du document* or de/fr/en (`--lang`, §4bis). They are **checks and never actions**: choosing one says what the next compilation will carry, and nothing runs until the button itself is clicked — which is what lets a level and a language combine, as they do on the command line. The seven level entries share one exclusive group across both submenus, so the interface cannot ask for `--level` and `--uniform` at once. What is checked reaches Typst as the `--input` flags `cli.input_args` builds and as nothing else: *tel qu'écrit* passes no `--input` at all, which is what makes the report come out with the base level and the language the document itself declares (§4, §4bis). The button's tooltip names what is checked and is empty while both are the document's own, so the only thing it ever shows is a forced level or a forced language. ⚠️ `--all-levels` and `--skip-data` are deliberately not offered (§13). ⚠️ The choices live on the window and not in `settings.json`: they survive a language switch and a reload, and the menu opens at *tel qu'écrit* at every launch.

**The RFEM tab (v0.98, retired in 0.117).** *RFEM* stood in *Structure*, before *Modèles statiques*, and showed what the project's RFEM exports held. It was retired with the whole RFEM import on the engineer's request of 08.10.2026 (docs/decisions.md, «Retrait de RFEM») and is kept in `archive/rfem/` -- these paragraphs as they stood are `archive/rfem/docs/ui/window-rfem-tab.md`.

**The dependencies, checked on every start (v0.59).** As soon as the window is on screen — `open_project` queues `check_dependencies` after `show()`, a modal needing a window to sit on, and since v0.87 after `check_engine`, the project just opened coming before the machine's packages (above) — it compares what is installed against `requirements.txt` (`calc/tools/dependencies.py`, §11ter). A mismatch — a package missing, or a version other than the one this report was verified with — opens a message box offering to install the pinned versions; a match says nothing. In parallel, in a thread of its own, PyPI is asked whether anything newer exists: the answer comes back as a **banner with a button**, in a quieter blue than the stale-data banner above it, and never as a modal — the report was verified with the versions pinned, so an update is an offer with a rebuild behind it. Installing also rewrites the pin, in the same action, since installing without pinning recreates the mismatch from the other side. The PyPI request may fail — no network, a proxy — and then nothing is said at all. Nothing installs without a yes. An installed Woodcore asks neither question (v0.83): its packages are the ones frozen inside it, and pip has nothing to install them into.

**Woodcore's own updates, asked on every start (v0.89).** An installed Woodcore asks the website, once at each start and in a thread of its own, what the latest published version is: `version.json` at `https://woodcore.pages.dev/version.json` (`updates.FEED_URL`), which the site's build writes, naming the installer's Release on GitHub (§12). `update_gui.schedule` is called by `main()` once the first window is up, and never under `--self-test`; a checkout asks nothing — git updates it — and neither does a test run, unless `WOODCORE_UPDATE_CHECK=1` (`0` never asks, `WOODCORE_UPDATE_URL` names another manifest, and `"updates": {"enabled": false}` in the settings turns it off for good). Where the manifest names a version newer than this one, **not installed here already** — a folder of `%LOCALAPPDATA%\Programs\Woodcore\` holding its `Woodcore.exe`, this window then being an older one opened on purpose —, not set aside and not put off, a **window** says «Woodcore 0.90.0 est disponible — vous utilisez la version 0.89.0», with its notes in the window's language and a line saying the new version installs beside this one. **Installer** downloads the installer into `%LOCALAPPDATA%\Woodcore\updates\` with a progress bar that can be cancelled, checks its size and SHA-256 against the manifest and starts it — its own wizard, which opens the new version at its end; **Plus tard** puts the question off for 24 hours, a day and not a start, each project opening in a process of its own (§13); **Ignorer cette version** never offers that version again, and the next one is offered. A question already up — the lock's, the engine's — is let finish first. ⚠️ **What is refused rather than acted on**: a manifest without its shape (`updates.validate`), an installer not on HTTPS, or neither on the manifest's own host nor exactly in Woodcore's releases on GitHub (`updates.installer_address_problem`, v0.117), a download sent on out of HTTPS, a file of another size or another SHA-256 — deleted, never left under the name a later start would reuse. Without a network nothing is said and nothing is slowed down; a download that fails says why, and names the download page. Where the manifest names **the page of what the version changes** (`changes`, per language, HTTPS on its own host — `updates.changes`), the window links to it under the notes, «Ce qui change pour vous, et ce qu'il faut faire», opened in the browser; the notes are escaped, never read as markup. The link is newer than the published 0.89.0, so it shows from the version after it.

**The wheel scrolls and zooms; it never changes a value (v0.69).** Qt turns a wheel into a value change on a `QAbstractSpinBox`, a `QComboBox` and a `QSlider` whether or not the widget has the focus. In a window that is mostly forms inside scroll areas — which every editor tab is — that means a wheel meant to scroll a panel silently retypes whichever field happens to be under the pointer, and says nothing. It is stopped in **one place**: `calc/tools/nowheel.py` installs an event filter on the *application*, in `main()`, before any window exists. A per-widget subclass would have had to reach 28 spin boxes, 25 combo boxes and the style sliders across four modules — plus the spin boxes a delegate builds on the fly for a table cell, which are written down nowhere, and every widget added later. ⚠️ The event is eaten **and re-sent to the viewport of the enclosing `QAbstractScrollArea`**: eating it alone would be worse than the defect, since the wheel would then do nothing at all over a field and a panel could not be scrolled by pointing at the middle of it. ⚠️ **A `QScrollBar` is a `QAbstractSlider`** and is the one exclusion — it is the scroll bar itself. The canvases are untouched: `plan_canvas` and `statics_canvas` handle the wheel themselves, to zoom about the pointer, and neither is a guarded type. **Ctrl+wheel zooms the interface since v0.122** (issue #85) where nothing under the pointer zooms by itself: the same filter, before its guard, walking up from the widget under the pointer -- a drawing (`QGraphicsView`), a code editor, a Typst page (`QPdfView`) or a class saying `ZOOMS_ITSELF` keep their own zoom (`nowheel.OWN_ZOOM`).

**The left pane sorts into folders (v0.69).** `calc/tools/grouped_list.py` is the list the five editor tabs share: folder rows and entry rows, drag and drop, and the **Ctrl/Shift selection of the Windows explorer**; *Nouveau dossier · Renommer · Supprimer le dossier* on the right button. ⚠️ **A folder is a field, not a directory.** Each source carries a `group` string — the «Groupe» the engineer's own *Identité* box already names — so nothing moves on disk, the ids stay flat, the rule that *the id is the file name* (§3.3quinquies) is untouched, and no `show-*` call changes. Real subdirectories would have made `connectors/Halle/SD_01.json` either an id of `Halle/SD_01` or a name that no longer says where its file is, and neither is worth a tidier listing. The field is **optional and additive** — absent, empty or whitespace all read as the root — so no `schema_version` was bumped and no file needed migrating; `connector.py` carries it into `data/connectors.json` besides, so a reader need not open the source. ⚠️ **A folder holding nothing exists only in the window**: folders are *derived* from the `group` values in use, so an empty one has nowhere to live in the project, and the set of them is kept per tab **in the project file**, `gui.empty_folders` (v0.83, `project.set_empty_folders`; `katalog.empty_folders` until v0.96, still read and replaced at the first change) — written as they change (`MainWindow.save_folder_settings`). They were in the session's memory only until v0.75, the audit found, and lost at every close, then in the user's `settings.json` until v0.83, where one project's empty folders showed in every other's; the first project opened by v0.83 took them over. A drop does not move anything in the tree: the widget works out the target folder, emits `moved`, and the tab writes the field, exports and rebuilds — so what is on screen is always what is in the files, and a drop whose export fails leaves nothing half-moved. Removing a folder never removes what is in it; its entries go back to the root. ⚠️ *Moments polaires* takes a drop since v0.75, its list being the calculations filed by their own `group`. Until then it **showed** the folders — its connectors drawn under the folder each was filed in, read off the export — and took no drop: its left pane is a tree of connectors with their calculations beneath, which the schemas module replaces, and building a drag into it twice would be work thrown away. ⚠️ **Since v0.116 a folder is told from a file** (the engineer: «on ne comprend pas très bien ce qui est un fichier et ce qui est un dossier»). Installing is **winget**, on a yes and never otherwise: `winget list --id Typst.Typst -e` first, then `install` or `upgrade` with `--version`, its output shown; and in the same action **the pin is rewritten** — the comment of `requirements.txt`, `TYPST_VERSION` in `.github/workflows/site.yml` and in `packaging/build.py` (`typst_check.pin`), installing without pinning recreating the mismatch from the other side. After installing, the machine's and the user's PATH are read from the registry and the Typst `project.typst_executable()` finds is asked its version again; where an older one still comes first on the PATH, the message names it. ⚠️ **The engineer's Typst was not winget's** until 26.09.2026: `C:\Program Files (x86)\typst\typst.exe`, which `winget list` does not know, came before `%LOCALAPPDATA%\Microsoft\WinGet\Links` on the PATH, so an upgrade winget installed was installed and not used, and the window said so. He removed that folder; winget's is the only Typst on the machine, **0.15.1** since, and it is the one `project.typst_executable()` finds (§11ter).

**Reserved tabs.** *Combinaisons de charges* is in the window already and says that it is not implemented yet (§14). Each tab is one entry of the module's `TABS` list, so a calculation that starts exporting its values replaces its placeholder with a browser of its own; the Variables tab is the model to copy for a browser (the loads tab was until v0.117), the polar moments tab for an editor.

**The icon and the taskbar.** The icon is `calc/tools/woodcore.svg` — a «W» on a wood-coloured beam since v0.83, the Typst-Katalog's «T» until then (`typst-katalog.svg`) — a hand-written SVG: text, so it is versioned and diffed like the rest (§1bis), and Qt renders it sharp at every size a title bar or a taskbar asks for. Replacing the file replaces the icon. `main()` sets it on the application, so the window and its message boxes all carry it. The taskbar needs two more things, both Windows-only and both in `main()`. `SetCurrentProcessExplicitAppUserModelID(APP_ID)`, called before any window exists: without it the taskbar files the window under `pythonw.exe` and shows Python's icon. And `claim_taskbar_icon()`, which hands the window's icons to its window class before it is shown: Qt leaves the class icon generic, and on every launch tested without it the button came up with that generic icon — most likely because the taskbar asks the window for its icon as the button appears, and falls back to the class icon when the window, still laying itself out, is too slow to answer. ⚠️ Pinning the button to the taskbar would pin `pythonw.exe`, not Woodcore. That would need a shortcut carrying the same AppUserModelID, and a `.lnk` holds absolute paths that break on another machine syncing this folder, so none is made. An installed Woodcore is `Woodcore.exe`, which pins as itself; the build turns this SVG into its `woodcore.ico` (§12).

**What else Qt changed.** Closing the window while an export runs waits for the export to finish, then closes, since stopping it could leave `data/` half-written. Rows a search hid come back open or folded as they were. Qt scales every screen itself, so the window no longer scales its own pixel sizes, and a size remembered by the tkinter window, in physical pixels, is clamped to the screen. Secondary text takes the palette's grey, so the window also reads in Windows' dark mode.
