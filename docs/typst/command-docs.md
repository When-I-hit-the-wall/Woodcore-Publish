# The commands tab and the frozen examples

> Every command documented and exemplified; examples frozen and pre-rendered.
>
> Moved verbatim from CLAUDE.md (§10sexies) on 2026-10-07. The § numbers are kept as stable anchors: `docs/README.md` maps every § to its file.

## 10sexies. The commands tab — every command, and what it prints (v0.64, frozen in v0.65)

`commands.typ` re-exports the whole of `lib/` with a bare wildcard, which is what §10bis's one-import rule buys: a command added to the engine reaches every section at once. Its price is that **every top-level name of `lib/`** reaches every `Sections/*.typ` — 212 at v0.77, of which 63 are commands an engineer calls and 149 the engine's own helpers —, and nothing at the point of use tells the two apart — an editor's autocomplete offers `substituted-rhs` and `tokenize` beside `show-calc`.

Woodcore's **Commandes / Befehle / Commands** tab is where that is said. A tree on the left, the categories below and a last folded row for the rest; a panel on the right with the command's summary, its arguments and their allowed values, two calls to copy, and its worked examples — each behind an arrow, and each showing **the page Typst actually compiles it into**.

| Category | What is in it |
|---|---|
| Afficher un calcul de l'export | `calc-block`, the twelve `show-*` |
| Calculer dans le rapport | `var`, `var-line`, `var-unit`, `eq`, `unit`, `var-domain`, `val`, `verify` (§10quinquies), and `distance` (v0.87) — computed in the report from a diameter the call gives, like the lines before it, and read from `calc/norms/` rather than from the export |
| Vérifier un élément (SIA 265) | `member` and the eight `verify-*` (§3.3undecies, v0.88) — the member checks of SIA 265 4.2, computed in the report from the norm files of `calc/norms/` |
| Objets des documents | `doc-table`, `live-load-table`, `dead-load-table`, `doc-field`, `doc-checklist`, `doc-choice`, `doc-image`, `doc-plan`, `doc-signatures`, `show-norm-list` and `doc-value` (§3.3octodecies, v0.112) — what Woodcore writes between the tags of a section of a convention d'utilisation, a base de projet or the report; read from the export where a cell says `auto`, never from a file of their own |
| Lire les données | `find`, the `*-ids`, `var-of`, `value-of`, `moisture-class-of`, `plans-of`, the eight `get-*` |
| Mettre en forme | the three `fmt*` primitives, the three `render-*` |
| Le rapport et sa langue | `set-report-language`, `report-lang`, the eight `t*`/`tl*`, and the four settings `report-level`, `uniform-level`, `number-digits`, `report-language` |
| **Internes** (folded) | the helpers the wildcard also exports, signature and `file:line` only, under a line saying they are not commands of the report |

**Listing every command is an obligation, not a feature** (§2 rule 14). The tab is built from what `lib/` actually defines, so a command added to the engine and given no category does not quietly fail to appear — `tests/test_commands.py` refuses it, by name and by `file:line`, along with one that has no `///` block, an argument without a bullet, or fewer than two compiling examples. Placing a binding in *Internes* is the other half of the same obligation: a helper is not undocumented by neglect, it is documented as not being a command.

**Every word of it is read out of the `///` blocks.** There is no second description of a command anywhere: Tinymist's hover, `docs/typst-reference.xlsx` and this tab read the same text, which is §2 rule 1 applied to documentation. What the tab adds is not prose but *arrangement* — the category, the two calls, and the rendering.

**Which category a command is in is hand-written**, in `build_reference.py`'s `CATEGORIES`, and deliberately not derived. "Carries a `///`" is the obvious rule and the wrong one: it would admit `resolve-level`, `parse-unit`, `natural-unit`, `key-symbol` and `fmt-magnitude`, which are documented internals, and it would have excluded `position-ids` and the three settings, which are public and carried no header. A category is what a command is *for*, which is not a property of its file or its line. `tests/test_commands.py` holds the list in both directions: a category naming a command the engine no longer defines fails, and so does a public command with no header, no argument bullets or fewer than two examples. Everything not named falls to Internes by subtraction, so a helper added to the engine lands there by itself and harms nothing.

**Two calls, both built from the signature.** *Appel complet* writes every argument out at its own default and *appel minimal* the required ones alone — `#show-plan("Fluchttreppe", width: 100%, legend: true, highlight: none, detail: false, zoom: 1, axes: true, scale-bar: true, caption: auto)` beside `#show-plan("Fluchttreppe")`. The string arguments are filled from the export, so a copied call names a sheet, a plan or a connection that exists and compiles as pasted — the v0.28 rule extended from the loads tab to every command. Both are built by `build_reference.py`'s `call_complete`/`call_minimal` beside the older `call_*` functions, so §10ter's one-place rule still holds, and the **named** arguments are read off the parsed signature rather than written down: one added to a command reaches both buttons with no Python edit. Only three commands need a hand: `var`, `eq` and `val` take their positional tail through a `..rest`, Typst having no optional positional parameter, and `POSITIONAL_TAILS` names those slots — the named half of even those three is still derived.

**An example is compiled once, not at every viewing (v0.65).** Opening an arrow **loads a file**; nothing is compiled and Typst need not even be installed. The pages are rendered ahead of time by `calc/tools/build_examples.py` into `examples/out/`, and committed. Measured: twenty examples opened in 271 ms, thirteen milliseconds each, with no process started. Before v0.65 each first view cost a compile of half a second to a second, and paid it again on every machine and after every export.

The page is the report's own: `conf` from `config.typ`, then **16 cm wide** — an A4 less the report's two 2.5 cm margins, which is the measure its text is set to — and as tall as it needs to be, with no footer and no page number. So the line breaking, the font and the right-hand citation column are the printed page's, and what the reader sees is what the report will print. The level, the language and the decimals are written **into** the file rather than passed as `--input`: those two flags are read by `Statischer Rapport.typ` and not by the engine, so stating them here is shorter and one failure mode fewer.

**The examples are frozen, and that is the point (v0.65).** An example reads data — `#show-calc("snow-load", "SL")` needs a sheet called `SL` to exist — so until v0.65 the documentation moved when the project moved: renaming a sheet changed the picture, and deleting an id broke the example. A reference that follows the thing it documents is not a reference. So the examples are rendered against a **snapshot** of `data/`, kept beside them and refreshed only when somebody asks for it.

Which forces the shape of the folder. The engine finds its data by **relative path** — `lib/calc-engine.typ` reads `json("../data/…")`, `lib/i18n.typ` reads `json("../calc/i18n/strings.json")`, and since v0.87 `lib/distance.typ` reads `json("../calc/norms/…")` — so *where the engine file sits* is what decides which data a command sees. The only way to point it at the snapshot is to put a copy of the engine beside the snapshot:

```
examples/
├── data/                    the snapshot                     versioned, ~1.4 MB
├── calc/i18n/strings.json   likewise, i18n.typ reads it       versioned
├── calc/norms/*.json        likewise, distance.typ reads them (v0.87)  versioned
├── lib/*.typ                a copy of the LIVE lib/          generated, gitignored
├── commands.typ             imports that copy                 generated, gitignored
├── <command>-<n>.typ        one MWE per example               generated, versioned
└── out/<command>-<n>.png    its page                          generated, versioned, ~18 MB
```

⚠️ **`lib/` there is a copy, refreshed on every run, and deliberately not versioned.** The examples read frozen *data* on purpose but must exercise the **current** engine, or the compile check proves nothing; a versioned copy would quietly become a second engine. `tests/test_commands.py` compares it byte for byte with the real one and says to re-run the generator when they differ.

⚠️ **`--freeze` is a flag of its own, and nothing passes it automatically** — not `export_all.py`, which is why an export cannot silently drag the snapshot forward. Nor does the export run the generator at all: the examples read frozen data, so an export cannot change what they print, and re-rendering every page on every export would be churn for nothing. Regenerating is an act somebody performs when they have changed a fence or the engine.

**The MWEs are generated from the fences, and committed** (§2 rule 14 unchanged). The example is still written once, in the `///` block of the command it documents; the script writes it out as a real `.typ` you can open and compile by hand. Never edited there — edit the block and run the generator, and the diff shows what moved. That is the arrangement `docs/typst-reference.xlsx` already uses.

**Rendered in German, once.** Three languages would be ~37 MB of PNG for a gain the documentation does not need: it is written in English (§4bis), and the labels the data carries are German whatever the window is set to. So switching the window to French no longer re-renders the examples. An example that wants another language calls `set-report-language` itself — which is better, because the reader sees the command doing it.

⚠️ **One example is one document and one run.** Batching a command's examples onto the pages of one document would be cheaper and would be wrong: `#unit` sets the unit a dimension is printed in *to the end of the document* and `#var` writes into a document-wide registry, so example 2 of `unit` would be compiled under example 1's table. A fence therefore has to stand on its own, and one that is an excerpt fails — which is how four of the six fences that existed before v0.64 were found to be wrong, one of them naming a connection (`SD001-V1`) this project has not had for some time.

**A level selector 1 · 2 · 3** sits above the preview of any command whose signature takes a `level:`, and shows the same example's page at that level, rendered ahead of time like the others (`<command>-<n>-L1.png` and `-L3.png` beside the level-2 page) — which shows §3.7's three reports rather than describing them. The level is written into the example as `#report-level.update(n)`, never as `uniform`: `uniform` overrides a per-call `level:`, so an example written to demonstrate an override would stop demonstrating it. ⚠️ **There is no 0 in the selector** (v0.87, the engineer's choice): a report level cannot be 0 (§4), so `level: 0` is shown the way it is used, by **examples of their own** — `var`, `var-unit`, `eq`, `val`, `verify` and `var-line` each carry one declaring at level 0 what a line below then names. `var` and `val` also carry one with `domain: "<var-domain>"` and one with `domain: ("<calc domain>", "<instance>")`; `var`'s existed already, but sat after the `- key` bullet, where the block's parser read them as part of it — they stand above the bullets now.

**PNG, not SVG, and on evidence.** One page of this report exported with `--format svg` is 284 `<symbol>` definitions and 527 `xlink:href` uses — Typst writes every glyph as a `<use>` of a `<symbol>`. QtSvg implements SVG Tiny 1.2, which has no `<symbol>`, so the text would simply not appear. (It emits no `clipPath`, mask, gradient or CSS, so nothing else was ever in question.) The image is rendered once at 192 ppi and drawn at whatever width the panel gives it, through the device pixel ratio rather than resampled; rendering at the widget's width instead would put the window's size in the cache key and make every drag of the splitter a run of Typst.

**Two cases still reach for Typst, and both say so.** A committed page can be **missing** (a fence added and the generator not re-run) or **stale** (the fence edited since). The tab then compiles — against the **frozen** data, through `examples/commands.typ`, because a fallback reading the live export would disagree with every page beside it — and prints a line saying which of the two it was and to run the generator. It does not recompile silently: a committed page quietly replaced is a committed page nobody notices is out of date. Those renders are cached in `%LOCALAPPDATA%\Woodcore\examples`, outside the project like the plans' renders (§10quater). A failed render is never cached, and its message is reported **in the example's own line numbers** — Typst names a line of the file it compiled, and that file is an assembly.

⚠️ **A committed page can lag the engine**, and that is the price of the word *frozen*. Regenerating is deliberate, so a change to `lib/` does not churn every rendered page on every commit — but it does mean the image shows what the example produced when it was last rendered. What guarantees the example still *works* is the compile check, which runs against today's engine every time the suite does; what the image guarantees is only what it looked like.

**The snapshot is taken from the example project, never from the open one (v0.86).** `build_examples.py --freeze` copies the export of `tests/projet-exemple/` — a real project anonymised, blank pages for the architect's plans, no workbook, no client — unless `--project` names another, deliberately. Until v0.86 it copied whichever project was current, which since v0.81 is any project at all: the snapshot is committed into the program's repository, shared with developers, so freezing the engineer's own project would have put his architect's plans and his client's name into it, and the documentation would have named whatever ids that project had that week. The example project is also what the test suite works on, so the pages, the fences and the tests name the same things. Its export drawn in Woodcore can be brought up to date without the workbooks it does not carry — each domain's own `export()`, as Woodcore runs it on a save — and was, for v0.84's connector layout, before the v0.86 freeze, and again in v0.87 (schemas, static models, connectors, connections) before the snapshot was frozen once more: **221 examples, 221 rendered**, where v0.86 had 199. The frozen `examples/calc/norms/` — the tables `#distance` reads — is copied at the freeze like `strings.json`.

⚠️ **The snapshot ages, and one consequence of that is checked** (v0.65.1). `build_examples.dangling()` reports an example naming an id the **example project** no longer has (the project that happened to be open until v0.86, which reported every example of a connector the engineer had renamed while snapshot, fences and tests all agreed), the generator prints it as a warning and `tests/test_commands.py` fails on it. Deliberately *not* a comparison of the snapshot against `data/`: the snapshot is meant to drift, that being its purpose, so such a check would fire when nothing is wrong — which is worse than no check. What hurts is narrower, and is the case that actually occurred: the load workbooks were consolidated while v0.65 was being written, eight instances vanished, and only the two that a fence cited were a problem. Nothing would have said so; it was caught by hand, minutes before a commit. The check is itself held against a planted defect, since a guard that has never fired is a guard nobody has tested.

⚠️ **The snapshot ages.** Its ids are those of the day it was taken (`"SL"`, `"Velo-Unterstand"`, `"VU-MP-1"`), so an example and the copy button beside it will eventually name different things. Accepted deliberately: the button must name what compiles in the **real** report, and the example must not move. Where the export has nothing to name at all, the button shows a generic call rather than a placeholder that could be mistaken for a value.

⚠️ **One fence cannot be compiled and says so.** `show-check` reads an instance's `checks[]` and nothing in this project exports one (§14), so no call to it can compile. Its examples are written ` ```typ-dry `: shown, never run, with a line saying why. A ` ```typ ` fence is compiled and held by the test; `typ-dry` is the exception and `tests/test_commands.py` refuses to let it spread, naming any other command that reaches for it.

**The chrome and the documentation follow the window's language (v0.86).** The tab's own labels follow the window's language selector like every other tab, with keys prefixed `ref_` — `cmd_` was the loads tab's until v0.117, `vr_` is the Variables tab's —, and a key defined in two modules would be silently taken by whichever merged last, which `_check_strings` cannot see. The documentation is written in English in the `///` blocks and stays English there, which is §4bis's standing rule for the names of commands and arguments and for every message — and what Tinymist's hover and `docs/typst-reference.xlsx` show. In a French or German window the tab shows its translation, read from `calc/i18n/commands.json` by `calc/tools/command_docs.py`: one entry per public command, and in it one **unit** per paragraph and per argument, each carrying `en` — the English it translates — beside `fr` and `de`. A unit is **matched on its English, not on its position**, so a paragraph edited in lib/ since it was translated matches nothing and is shown in English, the pane saying how many passages are; `tests/test_commands.py` names every such unit, and every unit nothing matches any more. What is never translated: the code between backticks (a test holds each translation to the English's spans), the names of commands and arguments, the ids, the symbols, the types after `->`. The German is Swiss, never an ß; the French puts a space before a colon, as the window's own does.

**The prose is set as the blocks write it (v0.86).** `code` between backticks in the window's fixed font, `**bold**` and `*italic*` as such — across a code span too — and a `*` that is a symbol's (`F*_x,i`) left alone (`commands_tab.prose_html`). Until v0.86 the tab showed the asterisks and backticks they are typed with. The tree's one-line summary drops the markers, and a search finds a command by the words of either language.

**An example needs no project (v0.81).** `examples/` is its own Typst root: the frozen data, the engine copied beside it and, since v0.81, a `config.typ` of its own — the report's styling, copied — where the MWEs imported the report's until then, so the documentation's pages depended on whichever report sat next to the code. The tab's fallback render is handed to `typst compile -` on standard input, with `examples/` as its root, so it writes nothing but its page: the `.preview/` directory under the report's folder is gone, and with it the import prefix derived from its depth. Regenerated after the move, all 183 pages came out byte-identical.

**The tab reads the website's data, and is laid out as its command page (v0.94).** The engineer: «la liste des commandes, leur description et exemples dans le katalog ou le site internet doivent partager un même set de données (il ne faut pas dupliquer …). Tri en fonction des commandes». **One set**: the categories come in `build_reference.CATEGORIES`' order — «Calculer dans le rapport» (`formula`) first —, named and introduced by `calc/i18n/reference.json` (`command_docs.category_label`, `category_lead`), which also holds the words the reference says beside every command (`command_docs.word`: commands, arguments, returns, the two calls, «Exemple {n}», level, «Défini dans», the two notes); **which levels an example is shown at** is `command_docs.example_levels` alone, which the tab, `build_examples.py` and the site read; a page's signature, argument rows and calls are `command_docs.signature`, `arguments` and `calls`; and an example in a language is `command_preview.render_localised`, the document the site compiles too (`document(..., document_language=True)`). The tab's STRINGS keep only what reference.json does not say — the count, the columns' names, the page's notes —, 18 keys gone. **The pane is the site's page**: the category, the name, the signature coloured and wrapped, the paragraphs in the window's language with reference.json's note where some are still English, the arguments as a table (name, the type as badges, the default, «—» where required, the description), what it returns, the minimal call and the complete one where it differs — each a `CodeField` with «Copié ✓» —, every example with its code and its page, no longer folded behind an arrow (reversing v0.64), the import line and «Défini dans lib/file:line». The 1 · 2 · 3 buttons stand where `example_levels` gives three, and an example pinning its own level states the rule instead of showing a disabled selector. **The examples in the window's language**: German shows the committed pages; French and English are compiled on demand, one at a time in a thread with «Compilation…» meanwhile, and kept in the cache (`%LOCALAPPDATA%\Woodcore\examples`, the language in its key) — about 0.8 s each at the first look, some 6 s for `var`, nothing afterwards; where Typst is missing or fails, the German page with one line saying why. A German page missing or stale is compiled in German in that thread, where a `QProcess` did it. ⚠️ **A `level: 0` pins no page** (v0.94): `command_preview.fixes_level` took an example declaring at 0 for one pinned to a level, so the very examples showing level 0 had neither the selector nor their -L1/-L3 pages; `FIXES_LEVEL` reads no 0 now, the one place that says so, and ten examples — `var`, `var-unit`, three of `eq`, `val`, two of `var-line`, `verify`, `member` — are shown at 1 · 2 · 3 in the tab, the committed pages (276) and the site. Masking stays the site's alone.

👉 The tab lives in `calc/tools/commands_tab.py` with its renderer in `calc/tools/command_preview.py`, the arrangement `plan_tab`/`plan_canvas` and `statics_tab`/`statics_canvas` already use. ⚠️ Neither may import `woodcore_gui`, which imports them to fill its `TABS`; the few helpers they would borrow are small and restated.
