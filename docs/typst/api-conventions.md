## 10bis. Typst API conventions — doc comments and function reference

The `show-*`/`get-*` layer in `lib/calc-engine.typ` is the surface the engineer actually types against when writing `Sections/*.typ`. Three conventions keep it self-explanatory, and within reach, without forcing a re-read of `calc-engine.typ` every time:

**1. Triple-slash doc comments.** Typst treats `///` comment lines placed directly above a `#let` binding as structured documentation. Tinymist (the Typst LSP, used by the VS Code extension most engineers on this project already have) parses them and shows them as a hover tooltip on the function name — so the parameter list, types, and allowed values appear directly in the editor while writing `Sections/*.typ`, without opening `lib/calc-engine.typ`. Convention to follow for every public function in `lib/calc-engine.typ`:

```typ
/// Displays a whole calculation -- its values and steps, var by var in the
/// order the data states them -- at the given detail level.
/// - domain (str): a calculation domain, e.g. "snow-load", or a domain carried by a position.
/// - instance (str): the workbook sheet, e.g. "SL", or the position id.
/// - level (int, auto): 1 = result only, 2 = important calculation,
///   3 = full intermediate detail. auto = use the global report level
///   (the "report-level" state, §4).
/// - title (auto, none, str): auto heads the block with the instance name,
///   none prints no heading, a string replaces it.
#let show-calc(domain, instance, level: auto, title: auto) = { ... }
```

Once every `show-*`/`get-*` function carries this header, the Typst package `tidy` can generate a standalone reference page (HTML or PDF) straight from `lib/calc-engine.typ`, so the documentation can never drift out of sync with the code the way a hand-maintained doc file would.

**Documenting a command is part of writing it, and is not optional** (v0.64, §2 rule 14). A command is finished when Woodcore's commands tab can show it: a `///` block with a summary, one `- name (type):` line per argument, a `->` line, and at least two worked examples that compile — plus a category in `build_reference.CATEGORIES`, or a deliberate place in *Internes* for a binding nobody outside the engine should call. `tests/test_commands.py` fails on each of those separately, naming the command and its `file:line`, so a command cannot reach the report undocumented. 👉 The same rule is what keeps the *tab* honest: it lists what `lib/` defines, so a command left out of a category is a command a reader is told does not exist. Since v0.86 the obligation includes the translation: `calc/i18n/commands.json` carries each paragraph and argument in French and German, matched on the English it translates, and `tests/test_commands.py` names a unit whose English changed without it (§10sexies).

**A public command also carries its worked examples, in the same block** (v0.64). Two or three ` ```typ ` fences, each a fragment that stands on its own and names real ids of this project, set after the summary and before the `- param` lines. They are not decoration: Woodcore's commands tab **compiles** each of them and shows the page it produces (§10sexies), and `tests/test_commands.py` compiles them all, so an example that stops working is named rather than left to rot. One fence is one example — several in one fence would share a page — and a fence has to declare what it names, since each is compiled as a document of its own. The one that cannot be compiled at all is written ` ```typ-dry `, shown and never run.

👉 The convention now covers **all three files** `commands.typ` re-exports — `calc-engine.typ`, `formula.typ` and `i18n.typ` — and since v0.87 the fourth, `distance.typ`, whose helpers are listed under *Internes* though only `distance` reaches the sections (§10bis point 3); and every top-level `#let` in them, a state like `report-level` included. Until v0.64 the parser behind the workbook read the first file only and required a `(` after the name, so two thirds of the command surface was in no catalog at all.

**Four rules the tooltip depends on, and `tests/test_doc_comments.py` holds them** (v0.63.1 — each was broken somewhere when the test was first run):

- **Every declared parameter carries a `- name (type):` bullet.** An argument the tooltip does not mention is one the engineer cannot find.
- **A command never hides its arguments behind a variadic sink.** `#let eq(..args)` shows in an editor as `eq(args: arguments) -> any`, and every named argument — `unit:`, `level:`, `style:` — is then invisible. Named arguments are declared one by one; only the *positional* tail may be variadic, which it has to be, Typst having no optional positionals (`#var("R_k", 7, "kN")` and `#var("q_k11", "q_(k,11)", 1.729, "kN/m²")` are the same command). `var`, `eq` and `val` were sinks until v0.63.1.
- **Every block ends in exactly one `-> type` line**, a union written with `|` — `-> content`, `-> int | none`. For a command that prints, `-> content` is not a formality: it is what says the result can go in a `grid` cell, which `Sections/005` relies on for its two load cases.
- **The block sits flush against its `#let`.** A single `//` line between the two detaches it and the editor then shows *nothing at all* — `render-symbol` had carried one since v0.49, so the one function whose whole job is explained in its header was the one with no header.

**2. A stable, predictable call shape.** Every `show-*` function that reads a calculation record — `show-calc`, `show-input`, `show-check` — keeps the same positional-argument order — **`domain`, then `instance`**, then whatever it looks up inside — with everything else passed as a named argument with a sensible default (`level: auto`, `title: auto`).

- `domain` is a calculation domain (`"snow-load"`, `"dead-load"`) or a domain carried by a position (`"bending"`).
- `instance` is the workbook sheet the domain was read from (`"SL-Dach1"`) or, for a position's domain, the position id (`"T001"`).

One rule covers both, because Python already knows which kind a domain is: `resolve-source()` looks the domain up in `data/calculations.json` first and falls back to reading it off a position. `show-calc` is the exception to "then whatever it looks up inside" — it takes no third argument at all, rendering the calculation entire (§10bis table). Once an engineer has learned this order for `show-calc()`, it holds for the other three, the remaining `show-*` functions taking the one id they display (`show-position("T001")`, `show-plan("Pavillon")`), and the named arguments surface through editor autocomplete instead of needing to be memorized. Combined with `assert(..., message: "...")` checks at the top of each function — e.g. rejecting an unknown `level` or an unknown `domain` with a message that lists the valid values instead of failing deep inside the rendering logic — a typo produces an immediate, actionable error rather than a silently wrong PDF.

**3. One import for every command** (v0.40). Every `.typ` file of the report starts with the same line — `#import "../commands.typ": *` in `Sections/`, `#import "commands.typ": *` in `Statischer Rapport.typ` — and never names the functions it uses. ⚠️ **In a project in three documents (v0.111) the line is written from the Typst root** — `#import "/commands.typ": *` in every entry file and every section, whatever its folder, and a picture `image("/Images/…")` — which is valid at any depth and is what Tinymist sees (§12), and is what will let a section be copied from one document into another without being edited; a project laid out as one report keeps the relative forms. The report's `commands.typ` re-exports the whole of `lib/calc-engine.typ` and `lib/formula.typ` — the engine's copy in `_woodcore/lib/` since v0.82 (§12) — (and, through the first, `lib/i18n.typ`) with a wildcard, so a function added to the engine can be called in every section at once, and no import line is edited again when a command is added or renamed (§13). One rule follows for the engine: every top-level binding of those files reaches every file, its helpers included, so none may take the name of a Typst global (`text`, `table`, `h`, `round`, …), which it would then replace in every section and not only in the engine. Several names are not hyphenated — `var`, `eq`, `val`, `unit`, `verify`, `t`, `tl` among them — and none is a Typst global, checked against `dictionary(std)` at v0.77; another library file would be re-exported from `commands.typ` the same way. ⚠️ `lib/distance.typ` (v0.87), `lib/timber.typ` (v0.88), `lib/bibliography.typ` (v0.99) and `lib/document.typ` (v0.112) are the exceptions to the wildcard, deliberately: `lib/formula.typ` imports their commands **by name** — `distance`, the nine member checks, `show-bibliography`, `cite-norm` and `bib-note`, and the eleven commands of the documents' objects (§3.3octodecies) — so `commands.typ` exports those and none of their helpers, and `commands.typ` itself did not change. The chain `calc-engine.typ → bibliography.typ → distance.typ → formula.typ` is acyclic by construction: `bibliography.typ` imports from `calc-engine.typ` and from nothing else; and `document.typ` imports `calc-engine.typ` and `bibliography.typ` at its top and nothing from `formula.typ` — a value in a cell is `doc-value`'s, which reads the registry and the export through `calc-engine.typ`'s own lookups — so no import stands inside a body.

**Function reference table.** Every `show-*`/`get-*` function in `lib/calc-engine.typ` now carries the `///` header described above, and every `show-*` function validates its lookup-key arguments with `assert(..., message: ...)` as described in point 2 — the table below reflects the real, confirmed signatures (§10ter/v0.10).

| Function | Signature | What it does | Example |
|---|---|---|---|
| `calc-block` | `calc-block(positions, title: none, axes: none, description: false, level: auto, plan: none, body)` | Groups every calculation concerning the same position(s) into one framed block, headed by each declared position's summary and axes (§5). `positions` is one id or an array; `axes` is one string for all of them or one entry per position; `description` is passed through to each header's line, `#member`'s at level 1 since v0.94 (`show-position`'s until then). `plan: auto` shows, under the summaries, a detail of every position plan the block's positions are drawn on, with them highlighted; a plan id shows that plan (§3.3sexies). Every `show-*` call in `body` that reads a *position* is checked against the declared positions and panics if it reads one the block does not declare; a call reading a calculation domain's sheet is not checked (§8). Blocks nest. | `#calc-block("T001", title: "Schneelast", axes: "Achse X3 / Achse YC")[ ... ]`, `#calc-block("T001", plan: auto)[ ... ]` |
| `show-calc` | `show-calc(domain, instance, level: auto, title: auto)` | Displays **a whole calculation**, walked **var by var in the order the data states them** — so the sequence the report prints is a property of the data, not of this function. A var some step produces is rendered as that step: its `formula` in letters (carrying the norm citation and the step's `description` footnote), then the same formula **in numbers, set bold**, built by substituting each operand the step's `uses` names. A var no step produces is one row, `symbol = value`, with its `description`/`choices` footnote from level 2 — or *half* a row, where consecutive vars share a `group` (§3.3) and are joined by a semicolon (`C_e = 1; C_T = 1`), optionally named by a `group_label` on the var that opens the run (`Gebäude Geometrie: L = 20.18 m; B = 7.8 m`) or, since v0.84, by one on a var that *joins* a run already open, which names itself inside the row (`Bauteil 1: ρ_(k,1) = …; Bauteil 2: ρ_(k,2) = …`). A step that declares itself `inline` prints its letters, its numbers and its answer on **one** row instead of two; a row too wide for its width — that one row, or the numbers line of a step on two — is **stacked at its `=` signs** under its first line, as `#eq`'s formula is (v0.87, second half, §10quinquies), and a row that fits is set as before. A var that declares `keep` holds its row even where an intermediate step's substituted formula already shows its number (§3.3). A var that carries a **`heading`** puts a line of its own above the first row it prints — «Charakteristische Lochleibungsfestigkeiten für C24:», the block the Bemessungsbeispiele name before a run of formulas — and nothing at all where that row is not printed (§3.3). Bold marks the answer and only the answer: a step whose result is in `results`, or which the data marks `bold` (§3.3), sets its numbers line bold, an intermediate one does not — and the same predicate decides whose operands keep their rows. Two rules keep that from printing anything twice: an **intermediate** step's operands get no row of their own (its substituted formula already shows them), while a **result** step's operands — C_e, C_T, μ — keep theirs; and a formula stating a *bound* (`s_k = ... >= 0.9 kN/m²`) is not closed with `= result` but keeps the compact `mit x = ...` note, set after the formula on the same row, above a plain result row. `level` selects what is printed, but **which** value appears at which level is the data's decision: a var and its step carry separate `level`s (§3.1), so `h_ref` shows as a value from level 2 and grows its formula only at level 3 (§3.3bis). Each of the instance's `tables` is printed at the level *it* declares and on the side *it* declares (§3.3), in list order: above the values as the working behind them, its `totals` rows what the lines below carry forward, or below them as the answer they lead to, its `value` cells naming the vars it prints so those vars get no rows of their own. A result is never allowed to go missing: one no shown step produces is printed anyway. There is deliberately no step-name argument — `show-input` is what picks a single intermediate value out. `title: auto` heads the block with the instance name (what tells two cases of the same load apart), `none` prints no heading, a string replaces it. An unknown `domain` panics listing both the valid domains and the valid positions; an unknown `instance` raises an assertion error listing the valid ones. A *position* instance is scope-checked against the enclosing `calc-block` (§5); a *sheet* instance is not (a load belongs to no position, §8). | `#show-calc("snow-load", "SL-Dach1")`, `#show-calc("dead-load", "EL+AL-Fassade", level: 3)` |
| `show-input` | `show-input(domain, instance, name, level: auto)` | Displays one input variable as `symbol = value unit`, with its `description` and `choices` as a single footnote at `level >= 2` (§9). The one call that reaches for a named value: `show-calc` renders a calculation entire and never takes a var name, so this is how a report pulls one intermediate value into its own prose. An unknown `domain`, `instance` or `name` fails with the valid options listed. | `#show-input("snow-load", "SL-Dach1", "h_ref")` |
| `val` | `val(what, domain: none, type: "val+unit", unit: none, symbol: none, level: auto, label: none, descr: none, norm: none, norm-ref: "", note: "footnote", style: none)` | **One value, printed** — wherever it comes from, and the one command that prints one (§10quinquies, v0.80, which folded `fmt`, `inline-value` and `live-load` into it). `what` is a variable's name, a var object (`var-of(...)`, an earlier `#var`, an `#eq`) or a number written here; `domain:` says where a name is read — left out the innermost `var-domain` and then the report's own variables, a string that `var-domain`, a **pair** a calculation and its instance (`("snow-load", "SL")`, `("live-load", "A1")`). `type:` picks the part: `"val+unit"` (the default) `1.729 kN/m²`, `"val"` `1.729`, `"unit"` `kN/m²`, `"expression"` `s_k = 1.729 kN/m²`. Level 0 prints nothing, 1 the value, 2 adds the label, 3 the description with its choices and the citation, all as **one** footnote — inline there is no em dash to hang a label on and no column for a citation, so `level: 1` is what keeps a bare number in a sentence of a checking report. **`note: "line"`** (v0.87) sets them on the line instead, `value — label (description; citation)`, the `choices` and the orange line of a unit written over staying a footnote. `unit:` prints the value in another unit **without touching the one it is held in**, and says so in an orange footnote whose marker is orange too; a unit of another dimension is refused. `label:`/`norm:`/`norm-ref:`/`symbol:` state what a value carries none of, or replace what it does. **`style:`** sets whatever part it prints apart, as `#var`'s line is (v0.100). Inside a `var-line` it is one item of the row. | `#val("R_d")`, `#val("s_k", domain: ("snow-load", "SL"), type: "expression")`, `#val("q_k", domain: ("live-load", "A1"))`, `#val("I_p", domain: ("connection", "SD_01-8mm"), unit: "cm²")` |
| `var-line` | `var-line(label: none, norm: none, norm-ref: "", level: auto, sep: auto, body)` | Sets several declarations on **one line**, joined the way `show-calc` joins the vars of a `group` (§3.3): `R_k = 7 kN; k_dens = 0.806; γ_M = 1.7` (§10quinquies, v0.80). `#var`, `#var-unit`, `#eq`, `#val` and `#verify` each know they are in a row: they print inline, and their own label and citation become one footnote. **The engine writes the separators**, so a value a level hides takes its separator with it and a `;` is never typed after a `#var(...)`, where Typst swallows it. `label:` names the row before its first value, as a var's `group_label` does; `norm:` cites the whole row in the right-hand column; `level:` overrides every item's own — `level: 0` declares the variables and prints nothing at all, not even the space of a line; the row's own citation follows its items', in the column from level 3 (v0.85.1); `sep:` replaces the semicolon. | `#var-line[ #var("R_k", 7, "kN") #var("k_dens", 0.806) ]`, `#var-line(label: "Teilsicherheitsbeiwerte", norm: "SIA 265", norm-ref: "2.2.5")[ … ]` |
| `show-check` | `show-check(domain, instance, check-name, level: auto)` | Displays one entry of a calculation's `checks[]` (utilization ratio + status), following the same `(domain, instance)` shape and the same `calc-block` scope check. `level` is accepted for a consistent error on a bad value but currently unused — every check renders the same regardless of level, reserved for a future per-check detail split. | `#show-check("bending", "T001", "Bending utilization")` |
| `var` | `var(key, symbol, value, unit, domain: none, label: none, descr: none, level: auto, norm: none, norm-ref: "", note: "footnote", style: none, summary: false)` | Writes one variable down: stored under `key`, where every formula below names it, and printed (§10quinquies) — **inline since v0.87**, `symbol = value unit` as a word of the sentence, so calls on consecutive source lines run on in one paragraph and a blank line starts another; its label, description and citation then go into **one footnote**. **`note: "line"`** sets it on a line of its own as it was until v0.87, the label after an em dash, the description a footnote and the citation in the right-hand column (the three levels below describe that form). A symbol may carry its words unquoted — `"W_(y,erf)"` — each word math does not know being quoted before it is evaluated (`quoted-words`, v0.87). `label:` was `descr:` until v0.80 — one word for one notion, the engineer's own rule (§4bis), the word every other command already used. `symbol` is an optional second positional argument — the math source that is *printed*, `"q_(k,11)"` — and left out, the key itself is printed, requoted by `key-symbol`. `value` is a number, or a **var object**: `var-of(...)`, an earlier `#var`, an `#eq`. A var object brings its own unit, description and symbol, so a value out of the export prints as `data/` spells it — and a `unit` given beside it **converts** that value (v0.63: `#var("F", var-of(...), "N")` on a value held in kN prints 7000 N, where until then it replaced the label and left the number alone). Level 0 prints nothing (the variable is still stored), 1 the symbol, value and unit, 2 also the **label** — on the line, after the unit and set apart by an em dash, because what a variable *is* is read with it, the way `show-position` prints its own — and 3 also the **description**, as a footnote (§9's own form), and the citation, in the right-hand column (v0.85.1, v0.85.2; until then the citation was printed at every level and the label only at 3). `label:` and `descr:` write the record's two fields and **override** the ones a var object carries; `norm:`/`norm-ref:` do the same for its citation. **`style:` sets the line apart** the way `#eq` sets an answer (v0.100, the engineer: «ajoute à #var l'argument style comme pour #eq») -- `"bold"`, `"underline"`, or `"double"`, which rules it twice underneath in the document's own ink, `verify`'s own mark, for a value a section rests on. ⚠️ **The whole line is wrapped and not the value alone**: `R_k = 7 kN` comes out bold entire, which is what he asked for and what tells it from `#eq`'s own (§13). ⚠️ There is no `#let`: Typst gives a function no way to bind a name in its caller's scope, so the name is the string. A key is letters, digits and `_`, **never a `-`**, which a formula would read as a subtraction; and since v0.87 (second half) **every such key is accepted** and printed as a symbol written by hand would be — `M2` as M and 2, `FEd` as one word — but one starting with `_` and one a formula reads as an operation (`dot`, `max`, `sqrt`), where v0.79 refused any whose first part was not one letter or a Greek name (§10quinquies). Inline, the symbol is no longer parted from its value at a line break (v0.87, second half; `#var-unit` and `#val` likewise). **`summary: true` lists the variable in a summary table** (v0.99, `show-load-summary`, `show-line-load-summary`), which is how a load the export does not carry — a line load, a load read off a manufacturer's table — reaches one; **its unit decides which table**, kN/m² an area load and kN/m a line load, any other unit refused naming the two where the table is printed. It changes nothing about how the line prints, so a declaration at `level: 0` is listed like any other. |  **`domain:` says where the value is read** (v0.85), the spelling `val` already had: a **pair** is a calculation of the export and its instance, and falls back to the `var-domain` named after that instance for a name the export does not carry — which is where `show-polar-moment` publishes its forces; a **string** is a `var-domain` of the report, and the variable is copied out of it into wherever the line stands, which is what carries a result out of the column that computed it. Either way the var of this same `key` is taken with its unit, its symbol, its description and its citation, and nothing is written beside it. | `#var("R_k", 7, "kN")`, `#var("s_k", domain: ("snow-load", "SL"))`, `#var("R_k", 7, "kN", label: "Kapazität", norm: "Sherpa", note: "line")` |
| `verify` | `verify(relation, level: auto)` | States a relation between the report's variables, **performs it**, and marks the answer — double-ruled in green with a ✔ where it holds, in red with a ✘ where it does not (§10quinquies). The relation is a raw block naming the registry's keys, and either side may be a whole expression, read by the parser `eq` uses. **The printed sign follows the truth**: where `a <= b` does not hold the line prints `a > b`, so what is written is true and the ✘ is what says the relation the report *wanted* is not the one that holds. Level 0 prints nothing (the comparison is still made), 1 the symbols alone, 2 the numbers alone, 3 both — with the right-hand side reversed, `F_Ed = 2.037 kN ⩽ 4.969 kN = R_d`, so the two numbers meet in the middle of the line; a side that is a **whole formula** prints at level 3 its letters, the same with numbers and units, then its value, `F_Ed/R_d = 12 kN/24 kN = 0.5 ⩽ 1`, and a bare number the number alone (v0.87). A relation too wide for its line is **stacked at its signs**, as `#eq`'s formula is (v0.87, second half): its first side's letters, then `= <numbers>`, then `= <value> ⩽ <the other side>`, as much on each line as the width holds, the whole double-ruled with the mark on its last line; one that fits stays in its sentence, and is no longer split across two lines. A `*` multiplies, as `dot` does. The comparison is made on the **full** values, a tie absorbed at a relative `1e-9`; two sides of different dimensions stop the compile. Replaced `test` in v0.61, and is **not** called `eval`, which is a Typst global (§10bis). ⚠️ Untraced, and it carries no citation — the prose must, if it matters. | `#verify(`F_Ed <= R_d`)` |
| `var-of`, `value-of` | `var-of(domain, instance, name)`, `value-of(domain, instance, name)` | Data access, not display: the whole `var` object, or just its number, so a value can be **computed with** in Typst and bound to a reusable `#let`. Carries no `calc-block` scope guard — that guards what is printed under a header, not what is read into a variable — which is also what lets these work outside `context`, i.e. in a plain `#let`. Prefer `var-of` when the same variable is also displayed, so it is looked up once. | `#let s-k = var-of("snow-load", "SL-Dach1", "s_k")` then `#let x = get-value(s-k) * 0.65` |
| `eq` | `eq(key, ..rest, unit: auto, style: none, label: none, descr: none, level: auto, norm: none, norm-ref: "", value: auto, note: "line", summary: false)` | A calculation written **by hand**: the formula in letters, the same formula with the numbers and their units put in, and the answer **computed from the formula** — with a real unit algebra (§10quinquies). The result is stored under `key`, so the next line names it without redeclaring anything. The formula **names the registry's keys** and nothing else: there is no `where:`, and a name the registry does not hold stops the compile listing the names it does. Only whole words are substituted, longest key first, so `F` cannot eat the `F` of `F_Ed` nor the `n` of `ln`. `unit:` is optional: left to itself the answer comes out in the one unit the table names for that dimension — kN, kNm, mm, N/mm², … — which `#unit` sets (§10quinquies, v0.63). Given a unit of **another** dimension it does not stop: the answer is printed in the unit the operands were written in (an N times a mm is an `Nmm`) with a red line naming both. Level 0 prints nothing (the answer is still computed, checked and stored), 1 the symbol and the answer, 2 also the formula in letters and the `label:` (v0.85.1, what the answer *is*, printed after it as `#var` prints its own), 3 also the formula in numbers, the `descr:` as a footnote and the citation. ⚠️ The signature is `eq(key, ..rest, …)` (corrected v0.117, the table having said `eq(key, symbol, formula, …)`): `..rest` holds the optional printed symbol, then the formula, Typst having no optional positionals. It takes the same four as `#var` and `#val`, each overriding what the answer would otherwise carry (v0.85.2), and **`note:`** (v0.87): `"line"`, the default, is the placement just described; `"footnote"` gathers label, description and citation into one footnote on the answer and leaves no citation column. **A formula too wide for its row is stacked at its `=` signs** (v0.87, second half, §10quinquies): the symbol and the formula in letters on the first line, then `= <numbers> = <answer>` on as few lines as the width holds, each `=` under the first, the lines spanning the citation column and the citation standing at the end of the first; a formula that fits is set exactly as before. A **`*` is a product**, evaluated and printed as `·` (`star-as-dot`, v0.87), and the symbol may carry its words unquoted — `"G_(1,Ed)"` for `"G_(1,\"Ed\")"` (`quoted-words`). A sum of different dimensions, a `sqrt` of an odd power, an unreadable unit, a `value:` the formula contradicts: each stops the compile naming both sides.
